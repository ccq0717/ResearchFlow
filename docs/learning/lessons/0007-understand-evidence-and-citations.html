Lesson 0007 · 约 25 分钟

检索结果怎样变成可追溯结论

这节课解释为什么“搜到了网页”“找到了一段话”“报告写了一句话”和“这句话有证据支持”是四件不同的事。

先记结论：RAG 负责把相关资料带到模型面前；Evidence 和 Claim 的显式关系负责说明报告中的关键结论由什么支持。

1. 四个概念不要混用

概念回答的问题ResearchFlow 中的例子
Search Result搜索服务返回了什么候选？标题、URL、摘要、highlights
Source这次研究实际读取了什么？网页正文或本地文档片段
Evidence来源中的哪段原文与问题有关？原文 excerpt、解释、source_id
Claim报告准备表达什么关键结论？结论文本和 evidence_ids

2. 为什么 Search Result 不能直接当引用

搜索结果通常只有标题和摘要，可能被截断，也可能只是排序算法认为相关。ResearchFlow 先把实际读取内容转换成 Source，并记录来源类型、作者、发布时间、网页 URL，或者本地文件名和页码/行号。

Source 表示“研究过程看过它”，不表示“它支持某条结论”。

3. Evidence 为什么同时关联问题和来源

同一来源可能回答多个研究问题，一条研究问题也可能需要多个来源。Evidence 保存：

  • question_id：它在回答哪个问题；
  • source_id：原文来自哪里；
  • excerpt：可在 Source 正文中找到的原文片段；
  • summary：这段原文与问题的关系。

工作流会过滤无法在对应正文中找到的 excerpt，避免模型只给出一段看似合理、实际上并不存在于来源中的“引文”。

4. Claim 为什么需要显式 evidence_ids

Claim 是报告希望表达的关键陈述，例如“依赖漏洞扫描应同时覆盖直接依赖和传递依赖”。如果只把全部 Evidence 一次性交给模型，之后无法确定是哪条 Evidence 支持哪句话。

Claim 保存明确的 evidence_ids，形成：

Claim
  → Evidence
    → Source
      → 网页 URL 或本地文件定位

这条链路让前端能够展示“结论—证据—原始来源”，也让后端能够确定性检查关联是否完整。

5. Citation Audit 检查什么

CitationAudit 统计：

  • Claim 总数；
  • 拥有有效 Evidence—Source 链路的 Claim 数；
  • 引用覆盖率；
  • 未获得支持的 Claim ID；
  • 学术、官方、工业、社区等来源类型数量。

覆盖率 100% 只表示每条结构化 Claim 都建立了完整关联，不自动证明证据在语义上足够强，也不证明报告正文每个普通句子都正确。

6. 本地来源为什么也转换成 Source

Evidence 没有设计成“网页 source_id 或本地 chunk_id 二选一”。本地检索命中先转换成 origin=local 的 Source，网页和文件随后共用同一套 Evidence、Claim、审计和前端展示逻辑。

这减少了两套并行数据模型：区别保留在 Source 的 URL、文件 ID 和 locator 字段中，而不是扩散到整个工作流。

7. 引用正确性有三个层次

层次当前怎样处理仍可能失败
结构完整检查 Claim—Evidence—Source ID 都存在关联存在但语义不充分
原文可定位excerpt 必须出现在来源正文，本地保留页码/行号原文可能被断章取义
语义支持LLM 提取并由黄金样例人工抽查尚无自动事实裁判保证正确

可靠的研究产品不能把“有链接”误称为“结论已被证明”。当前项目明确展示能够确定性验证的部分，并把语义充分性保留为评测问题。

面试表达：项目没有把 RAG 命中直接当成引用，而是建立 Source、Evidence、Claim 三层领域模型和显式关系；确定性审计检查结构完整与原文定位，同时承认语义支持仍需要模型评估和人工抽查。
