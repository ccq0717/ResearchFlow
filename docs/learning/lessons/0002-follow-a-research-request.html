Lesson 0002 · 约 50 分钟

一次研究任务如何穿过前端、后端和数据库

学完这一课，你应该能从用户点击“开始研究”讲到 SQLite 写入记录，再讲到网页为什么跳转到研究工作区。

先建立全局视角：前端负责收集和展示，后端负责规则与流程，数据库负责持久保存。每一层只做自己的工作，通过明确接口协作。

1. 四个参与者

参与者当前技术主要职责
浏览器Chrome / Edge显示页面、发起 HTTP 请求、接收 SSE
前端应用Next.js + React管理输入和页面状态，调用后端 API
后端应用FastAPI + Python校验请求、执行业务流程、读写数据
数据库SQLite把任务、事件和报告保存到磁盘

“前端”和“浏览器”不是完全相同的概念：前端是我们编写的程序，浏览器是运行它的环境。“后端”和“数据库”也不是同一个东西：后端决定做什么，数据库负责可靠地保存数据。

2. 第一步：用户点击按钮

入口页面位于 apps/web/src/app/page.tsx。React 把文本框内容保存在 goal 状态中；表单提交时调用：

const run = await createResearchRun(goal);
router.push("/research/" + run.id);

第一行等待后端创建任务，第二行在成功后跳转到该任务的工作区。前端不会自己生成任务 ID，也不会直接打开数据库。

3. 第二步：前端发送 HTTP 请求

API 客户端位于 apps/web/src/lib/api.ts。它把 JavaScript 对象转换为 JSON，并发出请求：

POST /api/research-runs
Content-Type: application/json

{"goal":"调研 AI 代码生成工具的评测方案"}

HTTP 是传输方式，JSON 是数据格式，REST API 是项目约定的接口风格。三者相关，但不是同一个概念。HTTP 的基础模型可参考 MDN HTTP Overview。

4. 第三步：FastAPI 接住请求

后端路由位于 apps/api/src/researchflow/api/routes.py：

@router.post("/research-runs", status_code=201)
async def create_research_run(body, request):
    run = await application.create_run(body.goal)
    return ResearchRunResponse.from_domain(run)

路由的职责是把 HTTP 世界翻译成应用调用，再把应用结果翻译成 HTTP 响应。输入长度等结构规则由 Pydantic Schema 校验，真正的创建流程交给应用层。

5. 第四步：应用层组织一次用例

ResearchRunApplication.create_run() 按顺序完成：

  1. 整理用户目标并生成 UUID；
  2. 构造状态为 queued 的领域对象；
  3. 通过 Repository 保存研究任务；
  4. 保存第一条 run.queued 事件；
  5. 创建后台异步任务，执行配置选择的模拟或真实研究工作流；
  6. 立即把已创建任务返回给前端。

这里的关键是：创建接口不需要等待整份报告完成。它先返回任务 ID，耗时工作继续在后端执行，前端随后通过 SSE 查看进度。

6. 第五步：Repository 写入 SQLite

SqliteResearchRepository 隔离了业务代码和数据库代码。它把 Python 领域对象转换为 SQLAlchemy Row，然后执行提交：

session.add(row)
await session.commit()

当前共有十四张研究与知识内容表，此外还有运行控制表和 schema 版本表。下面先列出贯穿一次请求的六张核心表：

  • research_runs：一行代表一个研究任务及其当前状态和报告；
  • research_plans：保存真实研究模式生成的结构化研究计划；
  • research_events：多行代表任务运行过程中按序产生的事件；
  • research_tasks：保存每个研究问题对应的检索任务；
  • research_sources：保存实际读取的网页或本地来源；
  • research_evidence：保存来源原文片段及其问题关联。

其余表保存来源扩展、Claim—Evidence 关系、知识文档、文档片段、Embedding 向量和运行选择关系。它们最终保存在 var/researchflow.db 文件中，原始上传文件保存在 var/uploads。

7. 第六步：响应回到前端

后端返回 HTTP 201 和任务 JSON。前端拿到 run.id 后跳转到 /research/{id}。工作区先通过普通 REST 读取任务快照，再建立 SSE 连接接收后续事件。

点击开始研究→POST 到 FastAPI→返回任务 ID
写入 SQLite→后台工作流运行→SSE 更新网页

8. 出错时从哪里查

看到的现象第一检查点

提示创建失败Network 中 POST 请求及后端终端

9. 序列化和反序列化发生了什么

浏览器内存中的对象不能原样穿过网络。序列化是把对象转换成可传输的 JSON 文本；反序列化是接收方把文本解析成自己的数据结构。

TypeScript object
  → JSON.stringify / fetch json body
  → 网络字节
  → FastAPI + Pydantic
  → Python object

响应走相反方向。时间、UUID、枚举等类型在 JSON 中通常表现为字符串，双方必须通过 API Schema 对字段含义达成一致。

10. UUID 为什么适合任务 ID

UUID 全称是 Universally Unique Identifier，中文是“通用唯一标识符”。项目用 UUID 标识一次研究运行。相比从 1 开始的连续整数，它可以在应用内独立生成，也不容易让访问者猜出相邻任务地址。

UUID 不是访问权限。知道一个难猜的 ID 不能替代认证；在线 Demo 仍要使用访问码会话。

11. 请求生命周期和研究生命周期不同

生命周期开始结束
创建 HTTP 请求用户提交表单后端返回 queued 运行
后台研究运行Application 创建 asyncio Taskcompleted、failed 或 cancelled
SSE 观察连接研究页建立 EventSource终态、离开页面或网络断开

三者不能绑死：HTTP 请求结束后研究继续；SSE 断开后研究也继续；刷新页面后可以通过运行 ID 和数据库快照恢复展示。

12. 浏览器开发者工具怎么看一条请求

  1. 打开浏览器开发者工具的 Network 面板；
  2. 提交研究并找到 research-runs 请求；
  3. 查看 Request URL、Method、Status Code 和 Request Payload；
  4. 查看 Response，确认是否返回运行 ID 和状态；
  5. 若状态码非 2xx，再对照后端日志和稳定错误码。

Network 说明浏览器实际发送和收到什么；Console 更适合看前端运行错误；后端终端说明 Python 服务发生什么。不要只盯着页面上的一句通用提示。

13. 结构校验和业务校验为什么分两层

Pydantic Schema 能判断 goal 长度、document_ids 是否为 UUID；它不知道文档是否存在、是否 ready、是否使用当前 Embedding 模型。后者由 Application 与 KnowledgeLibrary 查询业务状态后判断。把数据库业务规则塞进字段 Schema，会让校验依赖基础设施，也更难复用和测试。

14. 如果用户连续点击两次会怎样

当前两个 POST 都可能创建独立 Run，只要没有超过并发和每日额度。按钮应在提交中禁用以减少误操作，但前端措施不是强一致保证。需要网络重试安全时，可以让客户端发送 Idempotency-Key，后端以唯一约束保存“Key→创建结果”，相同 Key 返回同一个 Run。

15. X-Request-ID 与 Run ID 有什么区别

Request ID 标识一次短 HTTP 请求，用于日志关联；Run ID 标识跨越很多请求和几十秒研究过程的业务执行。一次 Run 会对应创建、快照、材料、指标和 SSE 等多个 Request ID。排障时前者定位某次接口，后者串起整个研究生命周期。

16. 网络超时后能否判断创建失败

不能。浏览器超时只说明没有及时收到响应，服务器可能已经提交 Run。客户端若盲目重发可能重复创建。当前低风险 Demo 通过历史列表让用户看到已有记录；生产系统应使用幂等键，或者先查询请求结果再决定是否重试。

17. 请求路径速记

表单 → API 客户端 → FastAPI 路由 → 应用层 → Repository → SQLite

表单收集目标；API 客户端发送 JSON；路由接收 HTTP；应用层组织创建用例；Repository 转换并提交数据；SQLite 把记录写进本地文件。
