从零理解 SSE：服务器怎样持续通知浏览器

从全称、中文含义和应用场景开始，逐步理解 HTTP 流、事件格式、浏览器 EventSource、断线重连，以及 ResearchFlow 的真实前后端实现。

简短回答：SSE 的全称是 Server-Sent Events，中文通常译为“服务器发送事件”或“服务端推送事件”。浏览器先建立一条普通 HTTP 连接，服务器保持响应不结束，并以规定的文本格式不断向浏览器发送事件。它适合进度、通知、日志和状态变化等“服务器持续向客户端单向更新”的场景。

1. 为什么会需要 SSE

最常见的网页请求是“一问一答”：浏览器发出请求，服务器准备好完整响应，返回后这次通信结束。例如读取文章、提交表单和创建研究任务都适合这种方式。

但有些结果不是一次产生的。ResearchFlow 创建研究后，后端还要规划问题、搜索网页、检索本地资料、提取证据和撰写报告，可能运行数分钟。用户需要在等待期间看到不断变化的状态：

  • 研究已经进入哪个阶段；
  • 当前完成百分比；
  • 找到了多少来源和证据；
  • 任务最终成功、失败还是被取消。

这些信息由服务器产生，而且服务器产生时间不确定。SSE 正是为“服务器持续通知浏览器”提供的 Web 标准。

2. SSE 用在哪些领域

领域典型信息为什么适合 SSE
AI 与数据处理Agent 步骤、模型流式文本、批处理进度计算耗时，更新主要由后端产生
监控与运维构建日志、服务状态、告警服务器不断产生新的只读事件
内容与通知新闻更新、系统通知、订单状态客户端主要接收，不需要高频反向发送
金融与仪表盘行情摘要、指标变化可持续推送文本事件；极高频场景可能改用其他协议

SSE 不是专门为 AI 发明的。它属于浏览器 Web 通信技术；ResearchFlow 只是把它用于研究工作流进度。

3. 先理解“保持 HTTP 响应打开”

SSE 没有绕开 HTTP。浏览器仍然发出一个 HTTP GET 请求，服务器仍然返回状态码和响应 Header。不同之处是服务器不会立即结束响应体，而是隔一段时间追加一些字节：

普通响应：请求 → [完整 JSON] → 连接完成

SSE 响应：请求 → [事件 1] … [事件 2] … [事件 3] … → 服务器结束连接

这里的“实时”通常是事件产生后很快到达，不等于硬实时系统。网络延迟、代理缓冲、服务器轮询间隔和浏览器调度都会影响到达时间。

4. SSE 的正式响应类型

服务器必须把媒体类型设置为：

Content-Type: text/event-stream
Cache-Control: no-cache

text/event-stream 告诉浏览器：响应体不是一份普通文本文件，而是按照 SSE 语法持续出现的事件流。编码为 UTF-8。缓存通常要关闭，否则中间层可能保存或延迟事件。

5. 一条事件到底长什么样

id: 12
event: research.event
data: {"type":"research.sources.completed","progress":56}

每一行由“字段名、冒号、字段值”组成，最后必须有一个空行，表示本条事件结束。

字段作用ResearchFlow 怎样使用
data事件正文；可以出现多行放一个 JSON 字符串，携带业务类型、阶段、进度和消息
event给事件命名，客户端可按名称监听持久化事件统一叫 research.event
id记录客户端最后收到的事件标识使用运行内递增的 sequence
retry建议断线后等待多少毫秒再连接当前没有显式发送，使用浏览器策略
: 开头注释，客户端不会触发业务事件: heartbeat 用于保持链路活跃

data 本质上只是文本。浏览器不会自动知道里面是 JSON；前端收到后还要调用 JSON.parse。同理，SSE 本身不知道什么是“研究完成”，业务含义由应用定义。

6. 浏览器如何解析事件流

浏览器按行读取响应，收集同一事件中的字段。遇到空行时，它创建一个 MessageEvent，并根据 event 字段分派给对应监听器。如果没有 event 字段，默认触发 message 事件。

const source = new EventSource("/api/research-runs/123/events");

source.addEventListener("research.event", (raw) => {
  const event = JSON.parse(raw.data);
  console.log(event.progress);
});

source.onerror = () => console.log("连接暂时中断");
source.close();

EventSource 是浏览器原生接口，不需要额外安装客户端库。只要没有调用 close()，异常断开后它通常会尝试重新连接。

7. EventSource 的限制

  • 原生 EventSource 面向 GET 请求，不能像 fetch 一样自由设置请求体；
  • 不能随意添加 Authorization 等自定义 Header，常见身份方案是同源 Cookie；
  • 主要传输 UTF-8 文本，不适合直接推送大型二进制文件；
  • 连接数量、代理超时和服务器资源都需要控制；
  • 它是单向通道，客户端操作仍要通过普通 HTTP API 发送。

ResearchFlow 的 Demo 会话使用 HttpOnly Cookie，前端建立 EventSource 时设置 withCredentials: true，因此不需要把访问码或 API Key 拼进 URL。

8. SSE、轮询和 WebSocket 怎么选

方式通信方向特点适合
轮询 Polling客户端反复请求最容易理解，但无变化时也产生请求更新不频繁、实现极简
长轮询客户端请求，服务器等到变化再返回每次变化后重新请求兼容旧环境
SSE服务器 → 客户端基于 HTTP、文本事件、自动重连进度、通知、日志、文本流
WebSocket双向建立独立的全双工消息通道聊天室、协同编辑、实时游戏

ResearchFlow 的用户操作——创建、取消、重试——频率低且方向明确，用 REST；服务器进度是连续单向更新，用 SSE。没有高频双向通信，所以 WebSocket 会增加不必要的连接协议和状态管理。

9. ResearchFlow 后端怎样产生 SSE

入口位于 apps/api/src/researchflow/api/routes.py。逻辑可以拆成五步：

  1. 读取运行记录；不存在就返回 404，而不是建立一条无意义的流；
  2. 确定起始 sequence：取 Last-Event-ID 与查询参数 after 的较大值；
  3. 先发送一个不持久化的 stream.ready，表示流已经建立；
  4. 循环查询 SQLite 中 sequence 更大的事件，格式化后逐条 yield；
  5. 运行进入终态且补齐终结事件后，结束响应。
async def generate():
    sequence = max(last_event_id or 0, after)
    yield format_stream_ready(...)
    while not await request.is_disconnected():
        events = await application.events_after(run_id, sequence)
        for event in events:
            sequence = event.sequence
            yield format_event(event)
        if run_is_terminal:
            return
        await asyncio.sleep(0.2)

当前实现每 0.2 秒查看一次数据库事件。这里是后端内部的短间隔查询，不是浏览器不断发 HTTP 请求。连续 15 次没有新事件时发送 heartbeat，大约相当于 3 秒一次。

10. 为什么要设置 X-Accel-Buffering

X-Accel-Buffering: no

某些反向代理会先积累一批响应数据再一次性交给浏览器，这叫缓冲。普通网页这样做可能提高效率，但 SSE 会表现为“进度半天不动，突然一次跳很多”。该 Header 请求 Nginx 等兼容中间层不要缓冲事件流。真正部署时仍需检查平台是否尊重它以及连接超时时间。

11. ResearchFlow 前端怎样消费事件

research/[runId]/page.tsx 不是一打开就只等 SSE，而是：

  1. 先通过 REST 读取运行、计划、材料和历史事件；
  2. 取得历史最后一个 sequence；
  3. 以 ?after={sequence} 建立 EventSource；
  4. 收到计划或材料事件时，重新读取相应 REST 快照；
  5. 收到完成、失败或取消事件时，读取最终快照和度量并关闭连接；
  6. 组件卸载时关闭连接，避免页面离开后仍占用资源。

线路上的 event 统一为 research.event，真正的领域类型放在 data.type，例如 research.evidence.completed。这样传输协议保持稳定，业务事件仍可扩展。

12. 断线重连和事件去重

网络断开不等于研究失败，因为工作流运行在后端。事件已经按 sequence 保存在 SQLite。页面重新进入时先读取完整历史；自动重连时浏览器也可发送 Last-Event-ID。后端从已收到序号之后补发。

补发可能和前端已有事件重叠，所以 event-stream.ts 用 sequence 作为键合并，再按 sequence 排序。可靠事件系统通常要能容忍重复，而不是假设网络永远恰好只送一次。

13. 为什么事件不直接携带整份报告

SSE 事件只携带阶段、计数、进度和错误码等摘要。计划、材料和报告仍通过 REST 读取。这样可以：

  • 避免重连时重复传输大量正文；
  • 让 SQLite 中已提交的快照成为权威数据；
  • 让事件契约保持小而稳定；
  • 避免前端仅靠零散事件拼接出一个可能不完整的最终对象。

14. 常见故障怎样判断

现象可能原因优先检查
接口成功但页面没有更新事件名或 JSON 解析不一致Network 中事件内容、前端监听名称
进度成批出现代理或压缩层缓冲Content-Type、X-Accel-Buffering、平台配置
不断重连并收到 401Cookie、CORS 或凭证配置错误Origin、withCredentials、Cookie 属性
刷新后丢失旧进度只在内存广播，事件未持久化事件表和历史 REST 接口
任务结束但连接不关闭终态识别或终结事件顺序错误运行状态、终结事件和前端 close

15. SSE 能保证什么，不能保证什么

  • SSE 标准定义浏览器怎样解释事件流和重连，不自动保证业务事件绝不丢失；
  • id 与持久化补发能提高恢复能力，仍需要应用正确实现；
  • heartbeat 只能帮助维持或检测连接，不代表业务任务健康；
  • 连接成功只说明进度通道可用，不说明 LLM、搜索或报告质量正常；
  • HTTPS、认证、限流和代理配置属于完整部署的一部分，不由 SSE 自动提供。
面试表达：SSE 即 Server-Sent Events，是基于 HTTP 的服务器到浏览器单向文本事件流。ResearchFlow 用 REST 创建和读取权威快照，用 SSE 推送增量进度；事件按 sequence 持久化并支持 after/Last-Event-ID 补发，前端按序号去重，终态后重新读取最终快照并关闭连接。
