SSE 如何把后端进度实时送到网页

学完这一课，你应该能解释 ResearchFlow 为什么需要 SSE、一条 SSE 事件长什么样，以及前后端分别做了什么。

先记住一句话：SSE 是浏览器发起一次 HTTP 连接后，后端不立即结束响应，而是沿着这条连接持续发送事件。

1. 从一个具体问题开始

用户创建研究任务后，后端可能需要几十秒甚至几分钟完成规划、检索、分析和写作。如果前端只发送一个普通请求并一直等待，用户会看到一个没有变化的页面，不知道程序是在工作、卡住了，还是已经失败。

我们希望后端每完成一点工作，就告诉前端“正在检索资料”“分析完成 60%”“报告生成完毕”。这是从后端到前端的连续、单向更新，正适合 SSE。

浏览器发起连接→FastAPI 保持响应→持续发送事件

2. 它与普通 HTTP 有什么不同

普通 REST 请求SSE 连接
前端请求一次，后端返回一个完整结果前端请求一次，后端分多次发送事件
响应返回后连接结束任务运行期间连接保持打开
适合创建任务、读取报告适合进度、日志和通知

因此 ResearchFlow 同时使用两种方式：先通过 REST 创建任务，再通过 SSE 订阅该任务的进度。

3. 一条 SSE 消息长什么样

id: 12
event: research.event
data: {"type":"stage.completed","stage":"retrieving","message":"检索资料完成"}
  • id：事件序号。断线重连后可以从下一条继续。
  • event：事件类型。前端可以针对不同类型注册处理函数。
  • data：实际数据。SSE 传的是文本，ResearchFlow 把 JSON 放在这里。
  • 最后的空行：表示这一条事件结束；没有它，浏览器可能继续等待。

服务端响应类型必须是 text/event-stream，事件流使用 UTF-8。完整规则来自 WHATWG HTML 标准。

4. ResearchFlow 后端做了什么

后端入口在 apps/api/src/researchflow/api/routes.py。阅读时先只找下面四件事：

  1. 路由 /api/research-runs/{run_id}/events 接受浏览器连接。
  2. 异步生成器 generate() 从数据库读取尚未发送的事件。
  3. yield 每执行一次，就向响应流交出一段文本。
  4. StreamingResponse 使用 text/event-stream 返回持续响应。
return StreamingResponse(
    generate(),
    media_type="text/event-stream",
)

当暂时没有新事件时，后端会发送 : heartbeat。冒号开头是 SSE 注释，浏览器不会把它当业务事件，但它能让连接保持活跃。

5. ResearchFlow 前端做了什么

前端页面在 apps/web/src/app/research/[runId]/page.tsx，核心是浏览器原生的 EventSource：

const source = new EventSource(".../events");

source.addEventListener("research.event", handleEvent);
source.onerror = () => setConnection("连接中断");

// 页面离开或任务结束时释放连接
source.close();

线路上的事件名统一是 research.event，具体业务类型（例如 stage.completed 或 research.evidence.completed）位于 data.type。前端解析 JSON 后更新 React 状态；React 再根据新状态重新显示进度条和研究事件。浏览器端标准用法可参考 MDN SSE 指南。

6. 为什么不直接使用 WebSocket

WebSocket 支持前端和后端随时双向发消息，但 ResearchFlow 当前只需要后端推送任务进度。SSE 基于普通 HTTP，浏览器自带 EventSource 和自动重连语义，模型更简单。技术不是越强越好，而是要和问题匹配。

如果未来加入多人协作编辑或高频双向控制，WebSocket 才可能更合适。可对照 Web 通信方式速查表。

7. 断线意味着任务失败吗

不意味着。SSE 连接只是“看进度的窗口”，研究任务本身运行在后端。关闭网页可能会让前端看不到新消息，但不应该自动把研究任务判定为失败。

ResearchFlow 为事件保存递增序号。浏览器重连时可以使用 Last-Event-ID 告诉后端最后收到哪一条，后端再补发后续事件。这也是为什么事件需要持久化，而不能只存在内存中。

8. 三个容易混淆的结论

  • 创建操作只需要一次明确响应，因此使用普通 REST；研究进度是后端在一段时间内产生的多次单向更新，因此使用 SSE。
  • SSE 用空行标记一条事件的边界；缺少空行时，浏览器可能认为事件尚未结束而不触发处理函数。
  • SSE 连接只是进度展示通道，工作流运行状态属于后端，两者生命周期不应绑定。
