Lesson 0022 · Interview Deep Dive

怎样证明系统可用，并诚实回答生产化问题

最后一课覆盖测试策略、CI、可观测性、容量、Docker、数据恢复、安全和演进路线，帮助你区分“Demo 跑通”与“可长期运营”。

1. 你如何证明项目是正确的

不能用“我手动打开过页面”作为唯一证据。当前验证分层：

  • 后端单元与集成测试覆盖配置、鉴权、数据库、Embedding、知识库、LLM 规划、LangGraph 与生命周期。
  • 前端组件测试覆盖 API、事件合并、材料、指标、Markdown 与公式。
  • Playwright E2E 启动前后端，从浏览器创建模拟研究、查看报告并刷新恢复。
  • 真实服务验收验证 LLM、Exa、Embedding 和真实 PDF 的集成，但不放进普通 CI。
  • 静态检查与生产构建发现类型、格式、依赖和构建期问题。

这些证据说明主路径和已覆盖边界在测试条件下工作，不等于不存在缺陷。

2. 为什么测试需要 Fake、HTTP Mock 和真实服务三层

层能证明不能证明
Fake业务流程、状态和数据关系可重复供应商真实协议
HTTP Mock Transport请求形状、响应解析、错误映射网络、认证和供应商当前行为
真实验收Key、网络、真实模型和 Provider 能协作长期稳定和所有输入质量

只用真实服务会慢、贵、波动且难定位；只用 Fake 又可能在 API 已变化时仍全部通过。

3. 为什么 CI 不读取开发者的 .env

CI 应从干净环境复现，普通测试不依赖个人 Key、额度、网络或本地数据库。Fake 与 Mock 让 Pull Request 自动检查稳定、低成本且不会泄露 Secret。真实验收应是显式、受保护、限额的独立流程，不应由任意外部 PR 获得生产密钥。

4. 当前 GitHub Actions 三个 Job 为什么分开

Backend、Frontend 与 Browser E2E 的依赖和故障域不同，分开可并行反馈，也能迅速判断问题属于 Python、TypeScript/构建还是跨栈用户路径。每个 Runner 是独立临时环境，不共享另一个 Job 安装的依赖；锁文件确保依赖解析可复现。

5. 代码覆盖率高是否代表质量高

覆盖率只说明哪些行或分支被执行，不说明断言是否有效、需求是否正确、测试数据是否代表真实输入。AI 项目还可能出现代码完全执行但检索质量下降。更有价值的是按风险设计测试：状态转换、事务边界、重连、恶意上传、模型无效输出和引用关联都比追求一个孤立百分比重要。

6. E2E 为什么最容易不稳定

它依赖浏览器、前端服务器、后端端口、启动时序、数据库文件和异步页面更新。此前 CI 失败就来自服务启动脚本与环境差异，而非 URL 断言本身。稳定 E2E 应使用健康检查等待服务、独立临时数据、确定性 simulation、明确超时、失败 trace，并确保 teardown 能终止子进程。

7. 什么是测试金字塔，在 AI 项目中够用吗

测试金字塔建议大量快速单元测试、适量集成测试、少量昂贵 E2E。AI 项目还需要一条“评测轴”：固定检索集、模型输出质量、人工 Rubric 和真实供应商兼容性。测试判断软件契约是否满足，评测判断开放输出是否足够好，两者互补。

8. 当前日志能回答什么

HTTP 中间件为每个请求读取或生成 X-Request-ID，记录方法、路径、状态码和耗时；工作流异常记录 run_id；持久事件记录面向用户的阶段变化与部分调用指标。它能关联一次 API 请求和一次研究运行，但当前不是完整分布式追踪，也没有统一 Trace ID 穿过 LLM、Exa 和 Embedding。

9. Logs、Metrics、Traces 有什么区别

  • Logs：离散事件文本与字段，适合解释具体错误。
  • Metrics：随时间聚合的数值，如请求率、P95 延迟、失败率、Token。
  • Traces：一条请求跨组件的父子 Span，适合定位时间花在哪一段。

当前项目有结构化日志与单 Run 指标雏形，尚未接入时间序列监控、告警和 OpenTelemetry Trace。

10. 应该监控哪些 SLI 和 SLO

SLI（Service Level Indicator）是实际测量值，SLO（Service Level Objective）是目标。例如创建 API 成功率、研究完成率、P95 总耗时、外部 Provider 错误率、SSE 重连次数、无引用 Claim 比例。作品集无需伪造 99.99% 目标；上线运营后应根据用户期望和成本设置，并用错误预算决定发布节奏。

11. 健康检查为什么不能只返回进程活着

当前 /health返回应用可响应和 workflow_mode，适合作为轻量 Liveness。更严格的 Readiness 应检查数据库是否可用、Schema 是否兼容以及必要配置是否有效；但不应每次都调用付费 LLM。Liveness 失败可重启进程，Readiness 失败应停止接收流量，两者用途不同。

12. 限流和配额为什么是可靠性功能

并发上限防止本机同时启动过多外部调用和数据库工作；每日运行额度限制成本与滥用。当前计数基于进程内 Task 和数据库日期，适合单实例。多实例会各自拥有内存计数且存在竞争，需要 Redis/数据库原子配额、用户身份和全局速率限制。

13. Timeout、Retry、Backoff、Circuit Breaker 怎样配合

Timeout 限制单次等待；Retry 处理暂时性失败；指数 Backoff 加随机抖动避免所有客户端同时重试；Circuit Breaker 在持续失败时快速拒绝，给依赖恢复时间。不能对所有错误重试：401 配置错误和格式错误通常立即失败，429/5xx/网络错误才可能重试。Exa 当前最多尝试两次，但没有等待退避；LLM 和 Embedding 当前主要做超时与错误映射。

14. 为什么重试会带来幂等问题

客户端超时不代表服务器没有执行。如果重试创建请求，可能产生两个 Run；若重试外部调用，也可能重复计费。当前产品的“失败后重试”明确创建新 Run，并用 retry_of 和 attempt 关联，不是网络级幂等创建。生产 API 可接受 Idempotency-Key，并在数据库中唯一保存请求结果。

15. 数据备份应该包含什么

SQLite 文件保存元数据、事件、材料和向量，uploads 目录保存原始文档；两者必须成对备份，否则数据库可能引用不存在文件。备份应在一致时间点完成，恢复后运行 SQLite integrity check、确认 Schema 版本、抽样读取文档并启动应用。只有复制动作没有恢复演练，不能证明备份可用。

16. Docker 解决了什么，没解决什么

镜像固定操作系统用户态、运行时、依赖和启动命令，容器提供进程与文件系统隔离，使 Windows 开发出的应用可在 Linux 容器主机一致运行。它不自动提供数据持久化、Secret 管理、HTTPS、备份、监控或高可用；这些仍需卷、平台和运维方案。

17. 为什么项目能在 Linux 运行

应用代码使用 Python、Node、HTTP、SQLite 和 pathlib 等跨平台能力，没有依赖 Windows COM、注册表或盘符业务逻辑。开发脚本同时有 PowerShell 侧重，但容器运行在 Linux。需要关注文件路径大小写、换行、权限、端口和持久卷挂载，而不是重写业务代码。

18. Docker Compose 是否必须

不是。它只是把前端、后端、端口、环境变量、网络和卷统一声明，减少手工启动差异。本地可以分别运行两个开发服务器；部署平台也可能直接使用各自 Dockerfile。Compose 的价值是编排多个容器，不是应用运行的硬依赖。

19. 为什么当前只能安全运行一个 API 实例

进程内 Task 只被创建它的实例知道，SQLite 写并发有限，本地 uploads 也未跨机器共享。负载均衡到另一实例时，取消可能找不到内存任务；多个写者还会放大事件 sequence 和配额竞争。单实例不是 bug，而是当前部署约束。水平扩容前需要共享任务队列、数据库、对象存储和分布式协调。

20. 在线 Demo 的最小安全清单

  • production 环境、research 模式、明确 CORS Origin。
  • 至少 12 字符访问码，前后端全程 HTTPS。
  • LLM、Exa、Embedding Key 只放服务端 Secret。
  • 限制运行次数、并发、上传大小、数量、页数和解析复杂度。
  • SQLite 与 uploads 使用持久卷并定期备份。
  • 日志不记录 Key、Cookie、全文文档或完整 Prompt。
  • 部署后验证登录、上传、研究、SSE、刷新、取消和恢复。

21. 为什么访问码不能保护多用户数据

通过同一访问码的所有访问者处于同一权限空间，可以看到相同历史和文档。Run ID 难猜也不是授权。真实多用户产品需要 user_id/tenant_id 写入数据模型，每次查询实施对象级授权，上传文件分租户存储，还要处理注销、会话撤销、审计和数据删除请求。

22. Secret 泄露后怎样处理

立即在供应商端吊销并轮换 Key，检查日志和 Git 历史，评估异常调用与费用，再更新部署 Secret 并重启服务。仅从最新文件删除并不够，因为旧 Commit、构建日志或镜像层可能仍保留。预防措施包括 .gitignore、Secret Scanner、最小权限、额度上限和独立环境 Key。

23. 数据库迁移与回滚怎样设计

先备份，再运行向前兼容迁移，部署能同时读取新旧结构的应用，确认后再清理旧字段。SQLite 不适合复杂在线迁移时可停机维护。回滚不仅是换回旧镜像：旧代码必须能读新 Schema，否则需要恢复数据库备份。当前版本检查会主动拒绝不兼容 Schema，这是安全失败而不是自动迁移。

24. 怎样做容量估算

先测单次运行的平均与 P95：研究问题数、网页请求数、LLM 输入输出 Token、总时长、文档 Chunk 数、向量维度和事件数。再结合每日运行量、并发、供应商限流和预算估算。向量存储近似为 Chunk 数×维度×每个浮点数大小，JSON 存储还有编码开销；当前不能只看 SQLite 文件初始大小推断长期容量。

25. 性能优化为什么先要 Profile

用户感受到的总时间可能主要在 LLM，而不是 Python；也可能本地大文档的 Embedding 成为上传瓶颈。先比较 Run 总耗时、LLM duration、搜索耗时、查询向量和数据库查询，才能决定并行搜索、缓存、批处理、索引或模型切换。没有测量的优化容易增加复杂度却不改善体验。

26. 缓存可以放在哪里，有什么失效问题

  • 相同查询的网页搜索结果：受时效、Provider 参数和授权影响。
  • 网页内容片段：需要 TTL，并尊重内容更新和使用条款。
  • 文档 Embedding：当前已按模型版本持久保存，本质上就是离线缓存。
  • LLM 结果：开放研究目标很难完全等价，还可能包含过时结果或用户资料。

缓存键必须包含模型、Prompt/策略版本、输入和关键参数；否则命中的是语义不同的旧结果。

27. 当前项目最值得优先改进的三件事

  1. 扩大评测：先建立有代表性的检索与报告质量集，知道系统在哪些问题上失败。
  2. 持久任务执行：若需要长期在线，引入队列和 Worker，支持可靠重投递与取消。
  3. 更完整的可观测性：记录每阶段耗时、外部依赖错误率和 Trace，同时保护敏感内容。

是否增加 BM25、Reranker、学术 Provider 或 Checkpointer，应由第一项评测发现的问题驱动。

28. 怎样回答“这个项目算完成了吗”

作为本地使用和作品集 Demo，核心需求、文档、测试、真实服务验证、容器和在线部署指南已经形成闭环。作为面向市场的多用户生产服务，它还没有完整认证授权、持久任务队列、多实例数据层、运营监控、SLO、规模化评测和合规体系。完成是相对于目标，不是软件存在一个永恒的“全部完成”状态。

29. 面试中怎样避免三个常见失分点

  • 只报技术栈：“用了 LangGraph”不是设计解释，要说明节点、状态、边界和没用 Checkpointer。
  • 把指标夸大：小基准 MRR=1 不等于真实场景准确率 100%，引用覆盖也不等于事实正确。
  • 虚构生产能力：明确单实例、进程内任务和 Demo 鉴权边界，再给出有顺序的演进方案。

30. 五分钟项目陈述结构

  1. 30 秒：用户问题和项目目标。
  2. 60 秒：规划—搜索/RAG—证据—报告主链路。
  3. 60 秒：模块化单体、Application 生命周期、SQLite 与 SSE。
  4. 60 秒：三次 LLM 调用、LangGraph 固定图、Source—Evidence—Claim。
  5. 45 秒：测试、真实验收、CI 与指标。
  6. 45 秒：当前局限和从评测、任务队列、可观测性开始的演进。
最终表达：这个项目的亮点不是堆叠框架，而是把非确定性的研究生成放进确定性的工程边界：可验证输入输出、可追踪状态事件、可定位证据、可复现测试和诚实的生产约束。面试时应始终用“代码现在做了什么”支撑结论。
