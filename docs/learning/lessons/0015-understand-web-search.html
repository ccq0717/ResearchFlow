Lesson 0015 · 约 55 分钟

搜索到网页，不等于获得可靠证据

这一课解释查询怎样生成、搜索结果怎样进入研究流程，以及为什么搜索排名和证据可信度是两个问题。

简短回答：ResearchFlow 通过可替换的 SearchProvider 调用 Exa 做通用网页搜索，并读取 Provider 返回的相关内容片段。LLM 负责生成检索词和理解材料，确定性代码保留 URL、来源关系并检查引用。系统可以搜论文页面、官方文档和企业博客，但当前没有学术数据库专有元数据能力，也不会自行抓取任意网页全文。

0. Information Retrieval 是什么

IR 全称是 Information Retrieval，中文是“信息检索”。它研究如何从大量信息集合中找到满足用户信息需求的内容。网页搜索、图书馆检索和 RAG 片段检索都属于这一领域。

用户真正想知道的内容叫 Information Need（信息需求）；输入搜索框的文字只是 Query（查询）。同一个需求可以有很多不同查询表达。

0.1 搜索引擎通常怎样工作

Crawling 抓取网页
  → Parsing 解析内容和链接
  → Indexing 建立索引
  → Query Processing 理解查询
  → Retrieval 召回候选
  → Ranking 排序
  → Results 展示结果

ResearchFlow 不自己抓取和索引整个互联网，而是调用 Exa 已建立的搜索能力。Provider 返回候选 URL、标题、元数据和与查询相关的 highlights。

1. 搜索、抓取和阅读的区别

阶段解决的问题产物
搜索 Search互联网上哪些页面可能相关标题、URL、摘要或高亮
读取 Read页面正文具体说了什么可交给模型的文本
证据提取正文中的哪段直接支持研究问题原文、解释和主张

搜索引擎的标题本身只是寻找候选页面的线索。当前 Exa 请求同时返回与查询相关的 highlights，网页读取器把这些已提取片段作为可读内容；它没有再抓取任意网页的完整 HTML。片段进入 Source 后仍要经过证据提取，不能把搜索排名本身当成事实证明。

2. 研究问题为什么还要变成检索词

用户问题通常适合人类交流，却不一定适合检索。例如“我该怎样公平评估 AI 编程工具？”包含模糊代词和多个意图。规划阶段为每个研究问题生成一条简洁英文 search_query，以覆盖论文、官方资料、技术博客等公开来源。

好的查询需要保留核心实体、比较维度和专业术语；过长会缩小召回范围，过短会带来大量噪声。当前由 LLM 一次生成，没有实现多轮查询改写或自动扩展同义词。

3. 召回和排序

  • 召回关注相关页面有没有进入候选集合；
  • 排序关注更有用的页面是否排在前面；
  • Top-K是在成本与覆盖面之间选择只读取前 K 个结果。

K 太小可能漏掉关键观点，K 太大会增加读取延迟、模型输入 Token 和噪声。外部搜索服务决定第一轮候选排序，ResearchFlow 当前没有再使用独立 reranker。

3.1 Precision 和 Recall 的直觉

  • Recall（召回率）关心所有真正相关内容中找回了多少；
  • Precision（准确率/查准率）关心返回内容中有多少真的相关。

放宽查询通常提高 Recall 但也带来噪声；限制只搜某个网站可能提高特定 Precision，却漏掉论文、规范和博客。研究系统需要在来源广度、阅读成本和上下文质量间平衡。

3.2 Ranking 依赖哪些信号

搜索服务可能综合语义相似、关键词、链接、时效和页面质量等信号，具体算法属于 Provider。ResearchFlow 不把 Provider 分数解释成事实可信度，也不假设第一名必然权威。

3.3 Query Rewrite 和 Query Expansion

Query Rewrite（查询改写）把自然语言问题变成更适合检索的表达；Query Expansion（查询扩展）加入同义词、相关实体或多个子查询。当前规划 LLM 为每个问题生成一条英文查询，没有多查询融合。

若后续发现召回不足，可以为同一问题生成多种查询并去重合并，但会增加搜索请求和阅读成本。

4. 为什么使用通用 Provider 接口

Workflow → SearchProvider.search(query, limit)
                         ▲
                         ├─ ExaSearchProvider
                         └─ FakeSearchProvider

ExaSearchProvider 负责认证、请求格式、超时和供应商响应解析；SearchResultPageReader 读取 Provider 已提取的内容。工作流只认识统一对象。未来换成付费质量更高的服务，主要新增或替换适配器，而不是重写领域对象。

5. 通用搜索能否替代学术 Provider

对当前“科研与技术预研”Demo，通用搜索能同时覆盖论文落地页、标准、官方文档和企业博客，范围更符合产品目标。因此项目没有强制接入只搜索某个学术站点的 Provider。

但通用搜索不等于专业学术检索。若以后要求稳定的 DOI、作者、期刊、引用次数、开放获取状态或按论文类型过滤，Crossref、OpenAlex 等专门数据源仍有价值。是否增加它们取决于产品需求，而不是“有网页搜索就永远不需要”。

6. 怎样判断来源质量

维度要问什么
相关性材料是否直接回答当前研究问题？
权威性是规范/论文/官方说明，还是无来源转述？
时效性结论会不会因版本、价格或政策变化而过时？
独立性多个来源是否只是互相转载同一说法？
可核验性是否保留 URL、标题和原文定位？

搜索排名只说明服务认为页面与查询相关，不自动证明正确。ResearchFlow 保存来源和原文、让 Claim 关联 Evidence，并展示引用覆盖；更高级的权威性打分、URL 规范化去重和来源多样性约束仍是可演进项。

6.1 Primary Source 和 Secondary Source

Primary Source（第一手来源）直接产生信息，例如论文原文、标准、官方发布和项目文档；Secondary Source（二手来源）对它们进行分析或转述。技术事实优先核对官方文档，效果与影响则可结合独立评测。

6.2 时效性为什么因问题而异

算法定义可能多年稳定，模型价格、API 参数和产品能力可能几周内变化。来源的新旧不能单独决定质量，要结合问题的时间敏感度，并记录发布日期与检索时间。

6.3 去重不只是字符串相等

当前项目按完全相同 URL 去重。现实网页可能有追踪参数、HTTP/HTTPS、尾斜杠、镜像站和转载内容。Canonical URL 规范化与内容指纹能做更强去重，但错误合并也可能丢掉不同版本。

7. 网页内容的现实限制

  • 动态 JavaScript 页面可能难以直接抽取；
  • 登录墙、付费墙和 robots 规则会限制访问；
  • 搜索 highlights 只是相关片段，不一定是完整上下文；
  • 页面可能更新或删除，之后无法复现原内容；
  • 网页内文字可能包含 Prompt Injection。

当前 SearchResultPageReader 使用 Exa 已提取的 highlights，不是通用浏览器爬虫，也不绕过访问限制。

8. 常见误区

  • “搜到了就是事实”：网页可能错误、过时或互相抄袭。
  • “结果越多报告越好”：噪声会提高成本并稀释关键证据。
  • “LLM 自己会联网”：模型只有在应用显式调用搜索并把结果放入上下文时才能使用这些网页。
  • “Provider 接口保证完全无成本迁移”：接口隔离业务，但不同服务的搜索语义、限额和内容字段仍需适配和回归测试。
面试表达：项目选择 Exa 通用网页搜索覆盖论文、官方文档和企业博客，并用 SearchProvider 隔离供应商；搜索只负责候选召回，后续正文读取、证据提取和引用审计共同约束报告质量。
