Lesson 0009 · 约 60 分钟

后台任务失败后，系统怎样保持状态可信

ResearchFlow 的研究可能运行数分钟。可靠性不是保证永不失败，而是让取消、失败、重启和重试都有明确且可恢复的结果。

先记结论：SQLite 中的 Research Run 是权威状态；内存任务只负责当前执行，事件负责解释状态怎样变化。

0. 可靠性不等于永不失败

Reliability（可靠性）关注系统在规定条件和时间内正确提供功能的能力。外部 API、网络、进程和硬盘都可能失败，可靠设计的目标是减少失败、限制影响、保留可信状态并提供恢复路径。

性质关注点项目例子
Availability 可用性现在能否提供服务健康检查、外部服务错误
Durability 持久性已提交数据是否保留SQLite、备份
Consistency 一致性相关状态是否互相符合终态与终结事件同事务
Recoverability 可恢复性故障后怎样回到已知状态中断标记、重试、恢复备份

0.1 状态机是什么

状态机用有限状态和允许的转移描述对象生命周期。Research Run 从 queued 进入 running，最后只能进入 completed、failed 或 cancelled 等终态。终态不应再次回到 running。

queued → running → completed
              ├→ failed
              └→ cancelled

显式状态机能拒绝“取消已完成任务”或“重复结束”等非法操作。

1. 创建接口为什么立即返回

FastAPI 先保存 queued 运行和 run.queued 事件，再创建后台 asyncio Task。浏览器马上得到 ID，随后用普通查询和 SSE 观察进度，不需要让一个 POST 请求等待整份报告。

2. 状态与事件为什么同事务终结

完成、失败和取消都通过 ResearchRunOutcome 写入。Repository 在一个事务里同时更新运行终态和追加终结事件，因此前端不会看到“状态已完成，但完成事件还不存在”的半成品。

3. 取消为什么要等待数据库操作

asyncio 取消会在一次 await 处抛出异常，但 SQLite 的提交可能已经在线程中开始。应用会屏蔽这次持久化操作的中途取消，等待提交或回滚结束，再传播取消，避免遗留写锁。

4. 进程重启后发生什么

后台 Task 存在于内存，进程退出后无法继续。下次启动扫描仍为 queued 或 running 的记录，将其标记为 RUN_INTERRUPTED。系统没有把失败误报为继续运行。

5. “恢复”为什么是新运行

当前 LangGraph 没有持久 checkpoint，所以失败运行会创建一个新的第二次运行，并保存 retry_of 与 attempt；原失败记录和中间材料保留。一次上限防止错误配置持续消耗额度。

行为当前语义
刷新页面恢复已持久化的同一运行
服务重启遗留运行明确失败
点击重试创建一次有谱系的新运行
断点续跑当前没有实现，也不会假装已经实现

5.1 Retry 和 Resume 不一样

Retry（重试）重新执行一次操作；Resume（续跑）从已保存的中间点继续。当前项目是带谱系的新运行重试，不是 LangGraph 节点续跑。重试外部调用还要考虑幂等性和重复费用。

5.2 Idempotency 是什么

Idempotency（幂等性）表示同一操作重复执行，对最终状态的影响与执行一次相同。GET 通常应幂等；创建研究的 POST 不是天然幂等，重复提交会创建不同运行。Repository 使用确定的主键和事务避免同一事件重复插入，但完整研究重试有意创建新 ID。

6. 限额和日志解决什么

并发上限保护单实例 SQLite 和外部服务；每日运行上限限制公开 Demo 的费用。JSON 日志只记录请求 ID、路径、状态和耗时，不记录目标正文、文档、密钥或供应商原始响应。

6.1 Timeout、Retry 和 Backoff

  • Timeout限制一次等待最长时间，防止资源永久挂住；
  • Retry适合暂时性错误，不适合认证失败等永久错误；
  • Backoff让多次重试之间逐渐等待，避免故障时继续冲击上游。

Exa 适配器对限流和 5xx 做有限尝试；LLM 超时会让本次研究失败，由用户决定是否创建一次新运行，避免不透明地重复昂贵生成。

6.2 Observability 是什么

Observability（可观测性）是通过系统输出理解内部状态的能力。日志、指标和追踪是常见支柱。ResearchFlow 记录结构化请求日志与运行度量，保留阶段事件；当前没有集中日志平台和分布式 Trace。

6.3 Backup 和 High Availability 不一样

备份帮助数据损坏或误操作后恢复，不会让故障期间服务持续在线；高可用需要冗余实例和故障切换。当前单实例 Demo 做备份恢复，不宣称高可用。

7. 怎样证明可靠性

生命周期测试覆盖完成、取消、重启中断、一次重试和配额；浏览器 E2E 覆盖创建、报告、度量和刷新恢复。备份恢复演练还会运行 SQLite 完整性检查。不同测试分别证明状态机、用户路径和数据可恢复性。

8. Crash Consistency 是什么

Crash Consistency（崩溃一致性）关注进程或机器在任意时刻停止后，持久数据是否仍处于可解释状态。项目用短事务保存阶段更新，用同一事务保存终态与终态事件；启动时将遗留非终态标记失败。它不保证恢复计算进度，但保证用户不会永远看到一个实际已不存在的运行仍在 running。

9. 取消与自然完成发生竞争时怎么办

用户点击取消时，工作流可能正好完成。Application 在 lifecycle lock 内先读取状态、取消并等待 Task，再重新读取数据库；若此时已进入终态，就拒绝再次取消。这样不会用 cancelled 覆盖 completed。并发控制的关键是操作前后重新验证，而不是只相信最初读到的状态。

10. 为什么 Retry 创建新 Run

覆盖旧 Run 会丢失错误、耗时、材料和审计线索。新 Run 用 retry_of和 attempt 建立谱系，原运行保持不可变历史。当前最多一次重试，并检查是否已有子尝试，避免用户反复点击造成无限费用。它是产品级重新执行，不是从失败节点 Resume。

11. At-most-once、At-least-once 与 Exactly-once

  • At-most-once：最多执行一次，失败可能丢失。
  • At-least-once：确保最终执行，但可能重复，需要幂等。
  • Exactly-once：外部效果看起来精确一次，通常依赖事务、去重和严格边界。

当前进程内任务接近一次尝试，重启后不自动重投；SSE 通知允许重复并由 sequence 去重。引入消息队列后通常采用至少一次任务投递，再让阶段写入和外部副作用幂等。

12. 可用性和数据持久性为何不同

服务暂时不可访问属于可用性问题；已完成报告在重启后丢失属于持久性问题。SQLite 和上传卷提高数据持久性，却没有备用实例；健康检查能发现不可用，却不能恢复数据。可靠性设计要分别回答检测、隔离、恢复和防止丢失。

13. 怎样定义降级策略

网页搜索失败但本地资料可用时，工作流可以继续并记录 warning；两类资料都没有才失败。这是有明确质量边界的降级。不能在 LLM 或 Embedding 完全不可用时悄悄返回“成功”假报告。降级必须让用户知道缺失了什么，并在指标中保留来源构成。

面试表达：项目把持久状态、内存执行和可重放事件分开；终态写入关注崩溃一致性，取消操作通过锁与二次读取解决完成竞争，失败重试创建有谱系的新 Run。当前选择重启后诚实失败而非伪装断点续跑，并用限额、日志和端到端测试形成可靠性闭环。
