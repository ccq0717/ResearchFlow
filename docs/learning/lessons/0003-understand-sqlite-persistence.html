SQLite、SQLAlchemy 和 aiosqlite 分别做什么

学完这一课，你应该能解释为什么 ResearchFlow 不需要启动数据库服务，以及一个研究任务怎样从 Python 对象变成磁盘中的记录。

最重要的结论：我没有为项目安装独立 SQLite 服务。SQLite 是嵌入应用进程的数据库引擎，ResearchFlow 后端直接读写一个数据库文件。

0. 数据库、DBMS 和 SQL 分别是什么

  • Database（数据库）是按结构组织的数据集合；
  • DBMS（Database Management System，数据库管理系统）是管理这些数据的软件；
  • SQL（Structured Query Language，结构化查询语言）是操作关系数据库的语言；
  • SQLite是一个嵌入式关系数据库引擎。

数据库文件不是普通 JSON 文件。SQLite 引擎负责页面格式、索引、锁和事务；应用应通过 SQLite 接口读写，不应手工编辑 .db 字节。

0.1 表、行、列和关系

关系数据库把一类实体放进表。列描述属性，行代表一条记录。不同表通过键建立关系：

research_runs
  id (Primary Key)  ←──── research_events.run_id (Foreign Key)
  goal                     sequence
  status                   type

Primary Key（主键）唯一识别一行；Foreign Key（外键）引用另一表的主键；Index（索引）用额外空间加快特定查询，但会增加写入成本。

1. SQLite 与 PostgreSQL 的直观区别

SQLitePostgreSQL 等数据库服务器
应用进程直接读写数据库文件应用通过网络连接独立数据库进程
不需要单独启动数据库服务需要安装、启动和维护服务
适合本地、单机和原型适合多用户、并发和生产部署

SQLite 官方将这种模式称为 serverless：这里不是指云函数，而是指没有独立数据库服务器进程。

2. 五层不要混在一起

层ResearchFlow 中的角色
数据库文件var/researchflow.db，真正保存字节
SQLite 引擎理解 SQL 和数据库文件格式，通常随 Python 的 sqlite3 支持一起提供
aiosqlite给同步 SQLite 操作提供适合 async/await 的接口
SQLAlchemy把 Python 类、查询和事务映射到数据库操作
RepositoryResearchFlow 自己定义的数据访问边界，隐藏具体存储细节

Python 官方提供 sqlite3 标准库接口；项目另外安装的是 aiosqlite 异步桥接包和 SQLAlchemy，而不是一个需要常驻运行的 SQLite 服务。

3. 读懂数据库连接地址

sqlite+aiosqlite:///./var/researchflow.db
│      │          └─ 数据库文件路径
│      └──────────── 异步驱动
└─────────────────── 数据库类型

这个地址来自后端配置。三个斜杠后的相对路径以启动后端时的当前目录为基准，所以项目统一要求从仓库根目录启动。

4. 数据库何时出现

后端启动时，app_factory.py 创建的应用生命周期函数调用 create_schema(engine)。database.py 随后执行：

await connection.run_sync(Base.metadata.create_all)

如果数据库文件或表不存在，SQLAlchemy 会根据模型创建它们；已经存在时则保留原数据。因此首次启动会自动生成文件，重启后历史记录仍然存在。

5. 十四张内容表怎样分工

research_runs目标、状态、阶段、进度、报告和时间一个任务一行

research_tasks研究问题对应的检索词和状态一个任务对应多个检索任务
research_sources网页或本地来源的标题、兼容 URL 和摘要每个来源属于一个检索任务

此外，research_run_controls 保存归档与重试谱系，schema_migrations 保存数据库结构版本；完整清单以核心数据模型为准。

research_plans.run_id 和 research_events.run_id 都指向所属任务。计划以任务 ID 为主键；事件序号和任务 ID 共同构成主键，使每个任务的事件能按顺序补发。检索任务、来源、证据和主张也用 run_id 归属到同一次运行。来源元数据和网页/本地来源属性放在独立扩展表中，因此旧数据库无需给原来源表破坏性加列。知识文档可跨运行复用，片段向量记录生成它的模型与维度；本地命中进入某次运行后仍转换成普通 Source，继续使用同一 Evidence 链路。

6. SQLAlchemy 帮了什么忙

没有 ORM 时，代码需要手写大量 SQL，并手动把查询结果转换成 Python 对象。当前项目用 ResearchRunRow 和 ResearchEventRow 描述表结构，再通过异步 Session 执行查询与提交。SQLAlchemy 的异步接口由官方 Asyncio 文档定义。

ORM 不等于数据库，也不会替数据库保存数据。它只是应用代码与数据库之间的翻译和管理层。

7. ORM 全称是什么，为什么不直接写 SQL

ORM 是 Object-Relational Mapping，中文是“对象关系映射”。面向对象代码操作对象，关系数据库操作表；ORM 负责在两种表示之间转换。

直接 SQLORM
查询细节明确，复杂 SQL 表达力强常见增删改查更统一，类型和映射集中
需要手工映射查询结果需要理解 Session、加载策略和生成的 SQL
不是“低级”方案也不会自动消除性能问题

ResearchFlow 使用 SQLAlchemy 不是因为 SQL 无用，而是希望集中管理表映射、异步 Session 和事务。排查性能时仍需要理解实际 SQL。

8. Transaction 为什么重要

Transaction（事务）把一组修改视为一个整体：要么全部成功，要么失败时回滚。例如研究进入 completed 和写入终结事件必须共同提交，否则前端可能看到“已经结束却没有结束事件”。

事务常用 ACID 概括：

  • Atomicity 原子性：一组操作不留下半成品；
  • Consistency 一致性：提交前后都满足约束；
  • Isolation 隔离性：并发事务互相影响受到控制；
  • Durability 持久性：提交成功后数据能在崩溃后保留。

ACID 是目标性质，具体保证取决于数据库、事务范围、同步设置和应用是否正确使用。

9. Session 是数据库连接吗

SQLAlchemy Session 表示一次工作的对象与事务上下文，不应简单理解为一条永久网络连接。它通过 Engine 的连接管理执行 SQL，跟踪对象变化，并在 commit、rollback 和 close 时完成相应处理。

项目为每次 Repository 操作创建异步 Session；异常时回滚，最后关闭。Session 不跨请求长期共享，避免多个异步任务同时修改同一个会话状态。

10. 两种 commit 不要混淆

  • await session.commit()：提交数据库事务，让本次数据修改生效；
  • git commit：记录源代码和文档版本。

它们只有英文单词相同，处理的是完全不同的系统。

11. 用只读命令观察数据库

停止后端不是只读查询的硬性要求，但初学阶段先停止后端更容易排除并发干扰。在仓库根目录执行：

.\.venv\Scripts\python.exe -c 'import sqlite3; db=sqlite3.connect("file:var/researchflow.db?mode=ro", uri=True); print(db.execute("SELECT name FROM sqlite_master WHERE type=? ORDER BY name", ("table",)).fetchall()); db.close()'

它使用 Python 自带的 sqlite3 接口以只读模式打开文件并列出表，不需要安装 SQLite CLI。详细备份和重置步骤见 开发与运维手册。

12. SQLite 的并发边界

SQLite 可以有多个读取者，但写入最终需要协调，作品集的单后端实例和较低并发适合这一模型。多个应用实例共享同一个普通磁盘文件会带来文件系统一致性、写锁和任务协调问题，不能只靠“数据库文件放在共享盘”解决。

这不表示 SQLite 不能用于任何生产环境，而是当前 ResearchFlow 的长任务、进程内 Task 和本地上传文件共同决定了单实例边界。

13. Schema 和 Migration 是什么

Schema 是表、列、键和约束的结构。项目首次启动可用 create_all 创建表；已有用户数据后，改变结构还要通过 Migration（迁移）有顺序地升级。schema_migrations 记录已执行版本。

直接删除数据库重新创建只适合可丢弃的开发数据。正式数据升级需要备份、向前迁移和回滚策略。

14. 为什么 MVP 先用 SQLite

MVP 全称是 Minimum Viable Product，中文是“最小可行产品”，指用足以验证核心价值的功能形成可运行版本，而不是粗糙或无需维护的产品。SQLite 占用资源少、没有独立服务、备份就是复制文件，非常适合 Windows 本地演示。代价是高并发、多实例部署和复杂运维能力有限。未来正式部署时可以迁移到 PostgreSQL；Repository 边界会降低业务层受到的影响，但数据库模型、迁移和部署配置仍需修改。

15. SQLite 的锁与 WAL 是什么

SQLite 允许多个读取者，但写入最终需要协调文件锁。WAL（Write-Ahead Logging，预写式日志）模式把新修改先追加到日志，通常让读取与写入更好并存，但仍不是无限并行写。当前项目没有把 WAL 当作必须配置；是否启用应经过当前文件系统、备份方式和负载测试。

16. 索引为什么能加速，也会增加成本

索引是按特定列组织的辅助数据结构，能减少全表扫描，但会占空间并增加插入更新成本。项目经常按 run_id、sequence、document_id 和模型筛选，这些查询是否需要复合索引应通过查询计划和数据量判断。索引列顺序影响可用性，不是“每列都建索引”就最好。

17. 什么是 N+1 查询

先查 N 个对象，再为每个对象单独查一次关联，会从 1 次变成 N+1 次数据库往返。Repository 当前读取材料时按类型批量取 tasks、sources、metadata、origins、evidence、claims 和关系，再在内存组装，避免逐 Source 查询元数据。批量查询也要关注一次返回过多数据的问题。

18. 为什么一个事务不能包住整场研究

LLM 和搜索可能等待很久。若整个研究始终持有数据库事务，会长期占连接与锁，失败回滚也会丢掉所有中间观察信息。项目使用短事务保存每次阶段更新，并只要求终态与终态事件原子提交。这是在可观察性、并发与一致性之间的取舍。

19. JSON 字段与关系表怎样选择

计划中的 questions 和 deliverables 作为整体读写，当前存成 JSON 较简单；Claim—Evidence 需要查询和验证多对多关系，因此使用独立关联表。若字段需要频繁过滤、关联、约束或独立更新，更适合正规化表；若只随聚合整体保存且结构稳定，JSON 可以减少表数量。

20. SQLite 备份为什么要考虑一致性

直接复制正在写入的数据库及 uploads 目录，可能得到时间点不一致的数据。可靠备份应使用 SQLite 备份机制或在受控时刻生成快照，并让数据库与原始文件成对保存。恢复后要运行完整性检查、确认 Schema 版本并抽样读取文档；未演练恢复的备份不能证明可用。

21. 三个持久化结论

  • SQLite 嵌入后端进程，后端直接读写数据库文件，因此不需要单独启动数据库服务。
  • aiosqlite 提供异步桥接；SQLAlchemy 管理映射、查询、Session 和事务。
  • 研究任务已经提交到磁盘中的数据库文件，所以后端进程退出后，历史记录仍然存在。
