Lesson 0017 · 约 60 分钟

怎样让 LLM 成为可靠的程序组件

Prompt 工程不是寻找一句“神奇咒语”，而是定义任务边界、输入数据、输出契约和失败处理。

简短回答：ResearchFlow 把 LLM 拆成规划、证据提取和报告写作三个窄任务；每次请求给出系统规则和业务数据，并要求 JSON Schema 结构化输出，再由 Pydantic 二次校验。模型负责语义判断，代码负责 ID 关联、状态和确定性检查。

0. Prompt、Context 和 Instruction

Prompt 常泛指发送给模型的输入；Instruction 是其中要求模型做什么的指令；Context 是完成任务所需的背景、材料和历史。Context Engineering 更强调选择、组织和控制模型可见信息，而不只是润色一句提示词。

Prompt
├─ System instruction：稳定角色与边界
├─ User request：本次目标
├─ Retrieved context：网页、本地片段、证据
└─ Output schema：程序期望的结构

0.1 Prompt Engineering 用在哪些地方

常见用途包括分类、抽取、摘要、生成、工具选择和多步骤 Agent。任务不同，成功标准也不同。证据抽取需要忠实和可定位，创意写作则可能更重多样性，不能用同一个 Prompt 模板解决所有问题。

1. Prompt 是程序接口的一部分

普通聊天只要求“回答看起来合理”；程序调用还要求字段齐全、类型稳定、ID 可关联、错误可处理。因此一个完整模型调用至少包含：

  • 角色与任务：这次只规划、只提取证据，还是写报告；
  • 边界：能否使用外部知识，遇到证据不足怎么办；
  • 数据：用户目标、研究问题、来源正文；
  • 输出契约：字段、长度、数量和格式；
  • 校验与失败：不符合契约时怎样转成应用错误。

2. 为什么拆成三个模型任务

调用输入模型负责
研究规划用户目标问题、理由、英文检索词、交付物
证据提取问题与来源正文原文、受支持主张、解释和关联 ID
报告写作计划、来源与已提取证据有引用的中文 Markdown 报告

单次“搜索完直接写长报告”很难定位错误。分阶段后，可以区分计划不合理、检索没命中、证据抽取错误和写作问题，每步也有更窄的输出契约。

3. System 与 User 消息

System 消息放稳定的角色、限制和输出要求；User 消息放本次研究目标与材料。来源正文即使包含“忽略之前指令”之类文字，也只是外部数据，不应被当作系统命令。

提示注入风险：只在 Prompt 里写“不要听网页命令”不能提供绝对安全。更稳妥的设计还包括最小工具权限、严格输出校验、限制外部内容影响的动作，以及对高风险操作进行确定性授权。本项目的模型没有任意执行系统命令的工具。

3.1 常见消息角色

角色通常用途
system应用级规则、身份、边界和高优先级要求
user用户请求以及应用组织后的本次数据
assistant模型此前输出；多轮对话时成为后续上下文
tool工具调用返回结果；当前自定义客户端未使用通用 tool loop

3.2 Zero-shot、Few-shot 和示例

Zero-shot 只提供说明，不给完整示例；Few-shot 在 Prompt 中放少量输入输出示例，帮助模型理解边界。示例会占用 Token，也可能让模型机械模仿。当前项目主要依赖明确说明和 JSON Schema，没有堆叠大量示例。

4. 结构化输出解决什么

模型响应
  → API 按 JSON Schema 约束格式
  → Pydantic 校验类型、长度、数量、额外字段
  → 代码检查 source_id / question_id 是否真实存在
  → 转换为领域对象

OpenAICompatibleLLMClient 使用 Chat Completions 的 JSON Schema 兼容格式。Schema 能减少解析不稳定，却不能证明内容事实正确；所以证据原文、ID 白名单和引用审计仍然需要。

4.1 JSON Schema 约束哪些内容

Schema 可以约束对象字段、字符串、数组长度、必填项和是否允许额外字段。Pydantic 根据 Python 模型生成 Schema，又在响应回来后重新验证。

Schema 不擅长表达“这个结论是否真的被网页支持”之类语义条件，因此代码还检查 ID 和原文，质量层还需评测。

5. Token 与上下文窗口

模型先把文本切成 Token。输入 Token 包含系统规则、用户目标、问题、来源正文和已有证据；输出 Token 是模型生成的 JSON 或报告。上下文窗口限制一次请求能够处理的输入与输出总量，不等同于模型“永久记忆”。

ResearchFlow 最大开销通常来自证据提取和报告写作，因为它们携带网页/本地片段及证据。减少无关来源、合理 Top-K、控制原文长度，往往比单纯缩短一行 Prompt 更有效。

5.1 Attention 和“长上下文”直觉

Transformer 模型通过 Attention 让不同 Token 相互关联。上下文更长意味着模型有机会看到更多材料，但不保证每段都被同等利用；噪声、位置和相似内容会影响结果。RAG 的价值之一就是先筛选上下文。

5.2 Temperature 是什么

Temperature 通常控制生成分布的随机程度：较低更集中，较高更多样。不同兼容 Provider 的支持和含义可能不同。当前客户端没有显式发送 temperature，使用供应商默认值；不能因此宣称输出完全确定。

5.3 Hallucination 是什么

Hallucination（幻觉）指模型生成看似合理但缺乏依据或错误的内容。RAG、严格 Prompt 和 Schema 能降低某些风险，却不能根除。ResearchFlow 通过原文校验、Claim—Evidence 关系和引用审计增加可核验性。

6. Token 统计与费用估算

项目读取供应商响应中的输入、输出和总 Token，累计到运行度量；若配置每百万输入/输出 Token 单价，则按用量估算费用。不同供应商可能另有缓存创建、缓存读取、推理 Token 或阶梯折扣，当前估算只覆盖配置的普通输入与输出价格，因此应标为近似值。

7. 为什么不能只相信模型的 ID

即使 Schema 要求 source_id 是字符串，模型仍可能写出不存在的值。适配器会根据本次输入建立允许的来源和问题 ID 集合，只保留可关联项；全部无效时返回稳定错误。语法正确和业务正确是两层验证。

8. 超时、连接与格式错误

错误含义
LLM_TIMEOUT服务在配置时间内未完成，不一定是代码错误
LLM_CONNECTION_ERROR域名、网络、Base URL 或连接层失败
LLM_HTTP_ERROR供应商返回 4xx/5xx，如密钥、额度或模型名问题
LLM_INVALID_RESPONSEJSON、Schema 或业务关联不符合契约

把错误分类后，前端可以给出可理解提示，测试也能验证行为。简单地 catch 所有异常并写“模型失败”会让排错非常困难。

9. 常见误区

  • “Prompt 越长越好”：冗余规则会增加成本和冲突，关键是任务边界清晰。
  • “JSON 正确就代表事实正确”：结构验证只保证形状。
  • “模型会记住上一次调用”：当前每次 HTTP 请求都显式提供所需上下文。
  • “让模型输出思维链更可靠”：系统需要可验证的证据和结果，不依赖保存模型私有推理过程。

10. 怎样迭代一个 Prompt

  1. 先定义可观察成功标准和失败案例；
  2. 把任务、数据和输出格式分开；
  3. 删除冲突、重复和无法验证的要求；
  4. 用固定评测集运行，而不是只看一个示例；
  5. 分析是检索、上下文、Schema 还是生成问题；
  6. 记录模型和 Prompt 版本，避免无依据地凭感觉修改。
面试表达：项目把 LLM 设计为三个有 Schema 的窄接口，结合 Pydantic 与业务白名单二次校验；模型承担语义规划、证据理解和写作，确定性代码掌握状态、关联与审计。
