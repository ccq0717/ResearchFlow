Lesson 0004 · 约 70 分钟

真实 LLM 是怎样接入后端的

学完这一课，你应该能解释模型 API、接口、适配器、Fake、结构化输出和环境变量分别解决什么问题。

先记结论：LLM 不是直接“装进网页”。浏览器把研究目标交给后端，后端通过 HTTP 调用模型服务，再把经过校验的研究计划保存到数据库。

0. LLM 的全称、中文和基本用途

LLM 全称是 Large Language Model，中文是“大语言模型”。它通过大量文本训练，学习根据已有 Token 预测后续 Token 的概率分布。聊天、摘要、分类、信息抽取和代码生成，都是在这一基础能力上设计输入和输出。

模型不是数据库，也不是搜索引擎：训练参数中的知识可能过时，输出可能不稳定或编造。ResearchFlow 因此显式调用网页搜索和本地检索，把可核验材料放进上下文。

0.1 训练和推理不要混淆

阶段发生什么ResearchFlow 是否做
Training 训练调整大量模型参数，需要庞大数据和算力否
Fine-tuning 微调用特定数据继续调整部分或全部参数否
Inference 推理给定 Prompt，使用已训练模型生成输出是
RAG推理前检索外部材料并加入上下文，不改变模型参数是

1. 当前有两种工作流模式

模式是否联网调用模型用途
simulation否默认演示、低资源运行、没有 API Key 时开发
research是规划、网页检索、证据提取和报告写作

模式由 RESEARCHFLOW_WORKFLOW_MODE 决定。默认值是 simulation，所以拉取仓库后不会意外产生模型费用。

2. 接口和适配器是什么

LLMClient 提供计划生成、证据提取和报告写作三个领域操作。调用方不需要知道 URL、Authorization Header、提示词和厂商 JSON。

研究工作流 → LLMClient → 研究计划
                    ├─ FakeLLMClient
                    └─ OpenAICompatibleLLMClient

适配器是接口的具体实现。Fake 返回固定但合理的数据；远程适配器发送真实 HTTP 请求。两者返回相同的 LLMPlanResult，因此工作流不需要写两套业务逻辑。

2.1 OpenAI-compatible 是什么意思

OpenAI-compatible 表示某个服务模仿一组常见 OpenAI API 路径和 JSON 形状，例如 /chat/completions、messages 和 usage。它不是供应商名称，也不保证所有扩展能力完全相同。

ResearchFlow 依赖 Chat Completions、JSON Schema 结构化输出和 usage 字段。更换兼容 Provider 时仍要验证模型是否支持这些具体能力、错误格式是否相近，以及 Token 统计含义是否一致。

2.2 一次模型 HTTP 请求有什么

POST {base_url}/chat/completions
Authorization: Bearer {api_key}
Content-Type: application/json

{
  "model": "模型名",
  "messages": [
    {"role": "system", "content": "任务规则"},
    {"role": "user", "content": "本次目标和资料"}
  ],
  "response_format": {"type": "json_schema", ...}
}

HTTP 200 只是供应商接受并处理了请求。适配器还要解析 choices[0].message.content、校验 JSON，并读取 usage。任一层不符合约定都应转为稳定应用错误。

3. 为什么测试使用 Fake

  • 不需要 API Key，不产生费用；
  • 不会因网络或供应商故障随机失败；
  • 输出确定，测试可以精确断言问题数量、模型名和 Token 数据；
  • 仍会穿过工作流、数据库和 API，能验证真实业务边界。

Fake 不是“假装测试全部真实能力”。远程 HTTP 格式另有 MockTransport 测试，而真实供应商的线上兼容性仍需在配置服务后单独验证。

4. 什么是结构化输出

普通模型回复是一段自由文本，程序很难稳定地提取字段。ResearchFlow 给模型一个 JSON Schema，要求返回摘要、3～8 个研究问题和交付物。Pydantic 再对返回内容做第二次校验。

{
  "summary": "计划摘要",
  "questions": [
    {
      "question": "要调查什么？",
      "rationale": "为什么要调查？",
      "search_query": "English technical search query"
    }
  ],
  "deliverables": ["最终交付物"]
}

“模型说它会遵守格式”不是保证；只有程序验证通过的数据才会成为 ResearchPlan。

5. 一次真实规划请求经过哪里

网页→FastAPI→Workflow →LLM API→SQLite
  1. 前端 POST 一个研究目标；
  2. 后端创建 Research Run；
  3. 工作流调用 LLMClient.create_research_plan；
  4. 远程服务返回 JSON，Pydantic 校验；
  5. 计划写入 research_plans；
  6. SSE 通知前端，前端再读取计划 API。

6. Base URL、模型名和 API Key

配置含义
Base URL模型服务 API 的根地址，例如包含 /v1
Model供应商识别具体模型的名称
API Key证明调用者权限的秘密凭证；本地兼容服务可能不需要

密钥只放在被 Git 忽略的 .env，不能写进 Python、README、截图或提交记录。前端也绝不能接收模型密钥。

7. 为什么记录耗时和 Token

耗时帮助判断用户等待发生在哪里；Token 是很多模型服务计费和上下文容量的基础单位。research 模式调用模型生成研究计划、提取 Evidence/Claim、撰写报告；网页搜索、正文读取、流程编排和引用结构审计不是模型生成。

运行页按输入、输出 Token 和配置的每百万 Token 单价估算 LLM 费用，不包含 Exa、Embedding 或部署平台费用，也不处理缓存 Token 等供应商特殊折扣。

8. Token 是字还是字符吗

Token 是模型分词器处理文本的基本单位，可能是一个汉字、词的一部分、标点或空格组合，并不固定等于一个字符或一个英文单词。不同模型的分词方式也可能不同。

Context Window（上下文窗口）限制单次请求可以处理的输入与输出总量。网页正文越多，输入 Token、延迟和费用通常越高，所以检索 Top-K、内容截断和结构化阶段拆分都是成本控制手段。

9. 为什么相同 Prompt 可能得到不同答案

生成过程依据概率选择 Token，服务实现和模型版本也可能变化。即使请求没有显式设置 temperature，也不能把远程模型当作绝对确定函数。结构化输出减少格式波动，证据审计限制可接受结果，但不会把语义生成变成传统确定性计算。

因此自动测试使用 Fake 固定输出；真实模型用代表性任务做验收，并记录模型名、Token、耗时和运行时间。

10. 失败时会发生什么

超时、连接失败、HTTP 错误和格式错误会转换成稳定错误代码。前端得到的是安全、可理解的消息，而不是可能包含内部地址、响应正文或密钥的异常堆栈。Research Run 会进入 failed 终态。

11. 三次 LLM 调用分别承担什么

阶段需要语义能力的原因不交给模型的部分
规划把开放目标拆成问题、检索词和交付物运行 ID、状态和持久化
证据提取理解原文与问题之间的语义支持来源 ID 白名单和原文是否真的出现
报告写作综合证据形成结构化自然语言报告Claim—Evidence 关系与引用覆盖检查

12. 真实研究模式的能力边界

research 模式把模型计划送入网页与本地资料检索，再让模型基于实际 Source 提取证据和写作。引用检查能验证关系完整，但不能自动保证来源质量、语义充分性或事实绝对正确。

13. Context Window 怎样分配

上下文窗口同时容纳 System Prompt、用户目标、研究问题、来源正文、证据和模型输出。来源越多不一定越好：无关内容会占 Token、稀释注意力并提高费用。项目先搜索和 Top-K，再把有限片段交给证据提取；报告阶段只使用计划、来源列表和已提取证据，避免再次携带全部原文。

14. 为什么不能自动重试所有 LLM 错误

网络中断、429 和部分 5xx 可能是暂时错误；401、模型不存在或 Schema 不支持通常重试也不会好。模型请求还可能已经产生费用但客户端没收到响应。自动重试必须限定错误类型、次数和退避，并记录 attempt；写入类操作还要考虑幂等。当前客户端主要做超时与分类映射，工作流把失败变成可见终态。

15. 结构化输出为什么仍会失败

供应商可能只“兼容”字段但不真正支持 strict Schema；模型可能返回被截断 JSON；代理可能改变响应格式；字段虽合法但 source_id 不存在。项目依次检查 HTTP、JSON 外壳、Pydantic Schema 和业务白名单。每层错误含义不同，不能全部显示成“模型不好”。

16. 怎样版本化模型行为

至少要记录 Provider、模型名、Prompt/Schema 版本、关键参数和运行时间。当前保存 Provider、模型、Token 与耗时，但 Prompt 还没有独立版本字段。若做严格评测，应给三类 Prompt 编号，并让结果可以按版本比较和回放。

17. Temperature、Seed 和确定性

Temperature 调整采样分布，较低通常更稳定但不保证完全一致；Seed 只在供应商支持时提供尽力而为的复现，后端、模型权重和并行计算变化仍会影响结果。当前客户端不发送 temperature 或 seed，使用供应商默认值。测试因此不比较真实模型逐字输出，而验证 Schema 和领域约束。

18. 费用为什么不能只看总 Token

输入与输出单价通常不同，部分供应商还有缓存读取、缓存创建、推理 Token、批处理或分层价格。项目只按普通输入和输出 Token 估算，且搜索与 Embedding 成本不在其中。这适合运行概览，不是财务账单；准确成本应解析供应商更细 usage 并保存计费版本。

19. 三个适配器边界

  • 稳定接口隔离了模型厂商细节，更换兼容服务时不需要修改业务流程。
  • Fake LLM 能确定性验证应用、工作流、持久化和 API 契约，但不能证明真实供应商在线或完全兼容。
  • HTTP 200 只说明服务器成功处理了请求，不保证响应满足业务字段、类型和数量限制，因此仍需 Pydantic 校验。
