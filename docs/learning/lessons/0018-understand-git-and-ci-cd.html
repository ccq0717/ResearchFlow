Lesson 0018 · 约 80 分钟

提交代码之后，自动化检查做了什么

Git 负责版本历史，CI 负责自动验证，CD 负责把通过验证的版本交付或部署。三者有关联，但不是同一件事。

简短回答：ResearchFlow 在 push 和 pull request 时由 GitHub Actions 分别检查后端、前端和浏览器端到端流程。当前只实现 CI，没有自动部署；因此绿色勾表示这些检查通过，不表示已经上线，也不证明没有任何缺陷。

0. Version Control 为什么存在

Version Control System（版本控制系统）记录文件随时间的变化，让开发者查看差异、恢复旧版本、并行开发和合并协作。Git 是分布式版本控制系统：每个完整 clone 都拥有本地历史，不是只能在线编辑 GitHub 文件。

Git 是工具，GitHub 是托管 Git 仓库并提供 PR、Issue 和 Actions 的平台。两者不是同一个产品。

1. Git 的四个位置

工作区 --git add--> 暂存区 --git commit--> 本地仓库 --git push--> 远程仓库
  • 工作区是你正在编辑的文件；
  • 暂存区选择下一次提交具体包含哪些改动；
  • Commit是带父节点、作者、时间和说明的版本快照；
  • 远程仓库用于协作和触发 GitHub 自动化。

Commit 不等于 push。合理的提交应表达一个完成的小阶段，既不必每改一行就提交，也不要把多个无关阶段挤进一个巨大提交。

1.1 Git 保存的是快照和关系

每个 Commit 保存项目快照的引用、父 Commit、作者和消息，形成有向历史。Commit Hash 是内容相关标识。分支只是指向某个 Commit 的可移动引用，因此创建分支通常很轻量。

A──B──C  main
    \
     D──E  feature

1.2 常用只读检查

  • git status：哪些文件修改、暂存或未跟踪；
  • git diff：工作区与暂存区的差异；
  • git diff --cached：下一次提交将包含什么；
  • git log --oneline：查看提交历史。

提交前先检查 diff，可以避免把 .env、运行数据或无关修改带入提交。

2. Branch 和 Pull Request

分支是指向某个 Commit 的可移动名字，使新功能能与稳定主线并行。Pull Request 是托管平台上的审阅和合并流程，不是 Git 本身的数据对象。CI 常在 PR 上运行，帮助审阅者先看到自动检查结果。

2.1 Merge 和 Rebase

Merge 创建或推进合并结果，保留两条历史汇合；Rebase 把一组提交重新放到新的基点，会改写这些提交的 Hash。共享历史上随意 rebase 可能给协作者造成冲突。当前项目无需为了“历史漂亮”频繁改写已推送提交。

2.2 Merge Conflict 是什么

当两条分支对同一位置做了 Git 无法自动组合的修改，就出现合并冲突。开发者要理解双方意图，编辑成正确最终内容，再测试并提交；不能仅机械选择“ours”或“theirs”。

3. CI 工作流的组成

概念在 GitHub Actions 中
Workflow.github/workflows/ci.yml 定义的一套自动化
Trigger当前为 push 和 pull_request
Job可并行运行的一组步骤，拥有自己的 Runner
Step检出代码、安装运行时、安装依赖、执行命令
RunnerGitHub 提供的临时 Windows 或 Ubuntu 环境

3.1 YAML 是什么

YAML 是常见配置数据格式，使用缩进表达层级。GitHub Actions 读取 .github/workflows/*.yml。缩进或字段位置错误会让工作流无法解析；具体语义由 GitHub Actions Schema 决定。

3.2 Runner 是临时机器

GitHub-hosted Runner 每次 Job 获得新的环境。它不会继承你电脑上手工安装的依赖或 `.env`。因此 CI 必须显式检出代码、设置 Python/Node、按锁文件安装依赖并安装 Chromium。

3.3 Job 为什么可以并行

没有 needs 依赖的 Job 可以在不同 Runner 同时运行。Backend、Frontend 和 E2E 互不共享内存或安装结果。一个 Job 安装过 Python，另一个 Job 仍需自己安装。

4. 当前三个 Job 检查什么

Job平台检查
BackendWindows / Python 3.12pytest、Ruff 规则和格式
FrontendUbuntu / Node 24组件测试、ESLint、Next.js 生产构建
Browser E2EWindows / Chromium启动前后端，从页面创建研究、查看结果并刷新恢复

Windows 后端和 E2E 覆盖主要本地使用路径，Ubuntu 前端也验证跨平台构建。三项并行能更快反馈，任一失败都会让整个工作流失败。

5. 为什么使用锁文件安装

uv sync --locked 和 npm ci 按仓库锁文件安装确定版本，避免开发机与 CI 因依赖自动升级产生不同结果。缓存只加快下载，不应改变最终解析出的依赖集合。

5.1 Dependency Cache 和 Artifact

Cache 缓存可复用依赖下载以加速后续运行，不应作为永久结果；Artifact 制品保存本次工作流产生的报告、日志或构建包供下载。当前 CI 使用依赖缓存，没有发布部署制品。

5.2 Secret 在 CI 中怎样处理

GitHub Secret 可以在明确步骤中注入敏感值，但来自不可信 PR 的工作流要格外谨慎。当前常规 CI 不需要真实 AI Secret，因为全部使用 Simulation、Fake 或 Mock。

6. 为什么 CI 不调用真实 LLM

自动测试使用 Simulation 或 Fake，结果确定、速度快、不需要 Secret，也不会每次 push 都产生外部费用。真实 LLM、Exa 和 Embedding 验收用于发布前人工验证，因为外部服务会受网络、额度、模型更新和随机性影响。

这不是说 Fake 能证明真实连接正常，而是把两类测试分工：CI 防止代码回归，真实验收确认供应商配置和端到端质量。

7. CI、Continuous Delivery 和 Continuous Deployment

术语含义当前项目
CI 持续集成频繁合并并自动构建、测试、检查已实现
Continuous Delivery 持续交付通过检查后形成可部署版本，通常由人批准发布未自动化
Continuous Deployment 持续部署通过检查后自动部署到生产未实现

因此把当前 GitHub Actions 简称为 CI/CD 并不精确。正式上线时可以增加镜像构建、部署环境 Secret、数据库迁移、健康检查、人工审批和回滚，但本地作品集无需为了术语完整而强行自动部署。

8. 绿色 CI 的边界

  • 只证明当前定义的检查在指定环境通过；
  • 没有测试到的路径仍可能有缺陷；
  • Fake 不能替代真实供应商验收；
  • 安全、可用性和报告质量还需要配置审查、真实示例与人工判断。

9. 一条成熟发布流水线还需要什么

代码审阅
→ CI 测试、静态检查、构建
→ 生成有版本的镜像/制品
→ 部署到预发布环境
→ 数据迁移与黄金路径验证
→ 人工批准
→ 生产发布
→ 健康监控与回滚

ResearchFlow 当前停在 CI 和可手工部署阶段。对本地作品集这已经合理；若提供长期在线服务，再根据实际平台实现 CD。

10. Git Object 为什么说明 Commit 不是“差异文件”

Git 用 Blob 保存文件内容、Tree 保存目录映射、Commit 指向根 Tree 和父 Commit。差异是比较两个快照计算出来的视图，而不是 Commit 的唯一存储形式。内容寻址让相同内容复用，也使修改历史对象会改变哈希。

11. Merge Commit 与 Rebase 的历史差异

Merge 保留两个分支的祖先并创建汇合 Commit，真实反映并行历史；Rebase 把提交复制到新基线，形成线性历史但会改变哈希。已共享分支强制 Rebase 会影响他人。选择取决于团队历史策略，代码最终内容可能相同。

12. CI Cache 为什么不能当 Artifact

Cache 用于加速可重新生成的依赖，可能被淘汰且不应成为唯一结果；Artifact 是某次运行需要保留或下载的测试报告、trace、覆盖率或构建产物。缓存命中失败应只让 Job 变慢，不应让构建无法进行。

13. Branch Protection 提供什么门禁

保护规则可以要求 Pull Request、指定检查通过、评审数量、禁止强推和要求分支最新。Workflow 只负责产生检查结果；没有分支保护时，维护者仍可能直接合并红色 Commit。自动检查与治理规则需要配合。

14. 为什么供应链要求 Pin Action 和依赖

CI Runner 会执行依赖安装和第三方 Action，它们拥有源码及可能的 Secret 权限。锁文件固定包版本；关键 Action 可以固定主版本或完整 Commit SHA，并使用依赖更新工具和漏洞扫描。来自 Fork 的工作流不应获得高权限 Secret。

15. Continuous Delivery 与 Deployment 的审批差异

持续交付保证每个通过检查的版本都可发布，但生产发布通常需要人工批准；持续部署则自动把每个合格变更推到生产。二者都需要构建不可变产物、环境配置、迁移、健康验证和回滚。当前项目只有 CI 与手工部署说明，没有自动发布流水线。

16. 一次可靠发布应怎样流动

Commit / Pull Request
→ 离线测试、静态检查、生产构建、E2E
→ 构建并扫描不可变镜像
→ 测试环境部署与真实服务验收
→ 备份和 Schema 兼容检查
→ 人工批准或自动发布
→ 健康、错误率和核心路径观察
→ 失败时回滚应用并处理数据兼容
面试表达：项目用三个 GitHub Actions Job 覆盖 Python、TypeScript 构建测试和 Windows Chromium 端到端主路径；外部 AI 服务使用 Fake 保持 CI 稳定，发布前另做真实验收。CI Cache 只加速依赖，Artifact 保存结果；分支保护、供应链固定、环境审批和回滚是从 CI 走向 CD 的必要补充。
