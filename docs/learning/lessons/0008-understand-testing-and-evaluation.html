Fake、Mock、集成测试与真实评测分别证明什么

AI 应用不能只靠“运行一次看起来不错”。这节课用 ResearchFlow 的测试分层解释怎样把代码正确性、协议兼容性和结果质量分开验证。

先记结论：自动化测试追求稳定、快速和可重复；真实服务评测确认外部兼容性与效果。二者互补，不能互相替代。

1. 为什么 AI 应用更需要分层验证

ResearchFlow 同时依赖数据库、后台任务、SSE、LLM、搜索和 Embedding。一次完整真实任务成功，不能定位其中某一层是否稳定；真实模型输出还会变化，外部网络和额度也会让测试偶发失败。

因此项目把问题拆成四类：

层次主要证明是否联网
纯逻辑测试计算和领域不变量正确否
Fake 集成测试完整应用流程和接口协作正确否
HTTP Mock 测试外部请求形状、响应解析和错误映射正确否
真实评测密钥、网络、供应商兼容性和当前结果质量是

2. Fake 是可预测的替代实现

FakeLLMClient、FakeSearchProvider 和 FakeEmbeddingClient 遵守与真实适配器相同的接口，但返回确定性结果。应用仍会经过 FastAPI、Application、LangGraph 和 SQLite，只替换不可控的外部服务。

例如 Fake Embedding 用文本特征生成固定向量，它不代表真实语义质量，但能够检查：

  • 上传后每个片段都有向量；
  • 查询和文档经过同一个接口；
  • 模型、维度或检索指令策略改变后会要求重新处理；
  • 本地命中能够进入 Source—Evidence—Claim 链路。

3. HTTP Mock 为什么仍然必要

Fake 不会真的组装 HTTP 请求，所以适配器还需要 HTTP Mock。test_embedding.py 检查 Gemini 请求是否使用正确端点、Header、批量结构、模型版本对应的任务指令和输出维度，也检查 OpenAI-compatible 响应是否按 index 恢复顺序。

这样可以在不消耗额度的情况下发现字段拼错、路径重复、返回数量不一致和非法向量等协议错误。

4. 为什么常规测试禁止读取 .env

如果测试继承开发者的真实 `.env`，切换到 research 后可能意外调用真实服务、消耗额度，甚至因为网络波动导致 CI 失败。测试创建 Settings(_env_file=None)，并显式注入 Fake 或 Mock。

“依赖注入”在这里不是抽象口号，而是让同一应用流程能够安全替换外部适配器。

5. 固定检索评测怎样工作

scripts/evaluate_local_retrieval.py 把三份公开样例导入临时 SQLite，用真实 Embedding 运行三个固定查询。每个查询预先记录期望排在第一位的文件。

  • Top-1 Accuracy：期望文档排第一的查询比例；
  • MRR@3：对期望文档的排名取倒数，再对查询求平均；未进入前三记为 0。
rank = 1 → reciprocal rank = 1
rank = 2 → reciprocal rank = 1/2
rank = 3 → reciprocal rank = 1/3

当前三条查询的两个指标都是 1.000。这证明固定样例链路跑通，不代表模型对所有语言、领域和大型知识库都同样优秀。

6. 真实端到端任务证明什么

一次真实 research 任务会同时经过 LLM、Exa、Gemini Embedding、本地文档、SQLite 和前端可读取结果。它可以确认部署环境中的 Base URL、密钥、模型权限和服务组合能够协作。

但真实成功不能代替回归测试：供应商明天可能变化，模型输出也不完全确定。项目把真实评测作为手动门禁，把 Fake/Mock 测试作为每次提交都能运行的基础。

7. 指标也需要解释边界

结果可以说明不能说明
后端测试通过已覆盖的行为没有回归不存在任何未测试问题
Top-1 = 1.000三个固定查询都命中预期文件真实语料检索质量完美
引用覆盖率 100%结构化 Claim 都有完整关联每条结论在语义上绝对正确
真实任务完成当前配置的外部链路可用服务永远稳定或没有费用风险

8. 当前验证策略

每次代码改动
  → pytest + Ruff
  → Vitest + ESLint + Next.js build

外部适配器或黄金场景改变
  → 固定真实服务评测
  → 浏览器端到端体验
  → 把结果和限制写入评测/复盘文档
面试表达：项目区分 Fake 集成测试、HTTP 协议 Mock、固定质量评测和真实端到端验证；常规 CI 完全离线，真实服务只作为明确授权的手动门禁，并且每个指标都说明它不能证明什么。
