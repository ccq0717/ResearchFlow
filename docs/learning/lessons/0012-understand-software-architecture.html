代码为什么要分层，接口为什么重要

这一课不背架构名词，而是回答一个实际问题：一条研究请求经过很多部件时，怎样避免所有代码互相依赖。

简短回答：架构是在约束“职责放在哪里、依赖指向哪里、哪些细节可以替换”。ResearchFlow 采用单体分层结构：一个后端进程内完成业务，但用领域对象和接口隔开 API、工作流、外部服务与数据库。

0. 软件架构到底是什么

软件架构是系统中重要组成部分、它们的职责和关系，以及长期约束这些关系的原则。它关注的是高成本、跨模块的决定，例如数据由谁保存、外部供应商怎样隔离、长任务由谁管理。

架构图不是架构本身，使用热门框架也不代表架构良好。真正需要观察的是：修改一个需求时要改多少地方，失败能否被隔离，模块是否能独立理解和测试。

0.1 高内聚与低耦合

  • Cohesion（内聚）：一个模块里的代码是否围绕同一职责；
  • Coupling（耦合）：一个模块对其他模块细节知道多少。

KnowledgeLibrary 把上传校验、文件保存、解析、分块和向量生成组织成一项完整知识库能力，属于较高内聚；如果每个页面都知道 Exa 的请求 JSON，就是不必要的高耦合。

0.2 单体、模块化单体和微服务

形式特点当前项目
混乱单体一个进程且内部职责纠缠不是目标
模块化单体一个部署单元，内部边界清晰后端采用
微服务多个独立部署服务，通过网络协作没有采用

微服务会引入服务发现、网络失败、分布式事务和独立部署。作品集 Demo 没有团队和扩展规模需要，模块化单体更合理。

1. 先区分模块、层和服务

  • 模块是代码组织单位，例如一个 Python 文件或包；
  • 层按职责和依赖方向组织模块，例如 API 层只能通过应用层发起研究；
  • 服务通常指可独立运行和部署的进程。

ResearchFlow 有多个模块和层，但后端仍是一个服务，并不是微服务。作品集规模下，单体更容易启动、测试和部署；清晰的内部边界已经能解决主要复杂度。

2. 当前后端的五层

层负责什么不应该负责什么
APIHTTP 路由、请求校验、响应与错误映射研究编排和 SQL

                    ↓            ↓
                 SQLite      LLM / Exa / Embedding

3. 依赖方向为什么重要

领域层描述“研究任务、来源和证据是什么”，不导入 FastAPI 或 Exa SDK。外层可以依赖内层的稳定概念，内层不应该反过来依赖易变的技术细节。这样更换网页搜索商时，不必重写研究任务和数据库模型。

常见误区：文件夹分得很多不等于架构清晰。真正的边界要看调用方向和数据类型；如果一个路由同时拼 Prompt、发请求、算向量并写 SQL，它仍然是紧耦合代码。

4. 接口与适配器

ResearchWorkflow、LLMClient、SearchProvider 和 EmbeddingClient 描述调用方真正需要的能力。Exa、Gemini 和测试 Fake 是接口背后的适配器。应用层依赖能力，而不是依赖某家供应商。

Application ──需要──> ResearchWorkflow
                         ▲
                         ├─ LangGraphResearchWorkflow（真实）
                         └─ SimulatedResearchWorkflow（测试/演示）

这叫依赖倒置：高层业务不直接绑死底层实现。它并不意味着每个类都要加接口；只有确实存在变化、外部 I/O 或测试替身的边界才值得抽象。

4.1 Python Protocol 怎样表达接口

Python 的 Protocol 可以声明“对象只要具有这些方法就满足接口”，不要求实现类继承共同基类。这称为结构化类型：

class SearchProvider(Protocol):
    async def search(self, query: str, *, limit: int) -> tuple[SearchResult, ...]: ...

ExaSearchProvider 和 FakeSearchProvider 只需提供兼容方法。类型检查帮助发现签名错误，运行时装配由 app_factory.py 完成。

4.2 Adapter、Repository 和 Facade

模式目的项目例子
Adapter 适配器把外部接口翻译成内部接口Exa、Gemini、OpenAI-compatible 客户端
Repository 仓储用领域语言封装数据访问SqliteResearchRepository
Facade 外观用一个较简单入口隐藏一组复杂协作KnowledgeLibrary

设计模式是描述解决方案的词汇，不必为了“用了模式”而增加无价值类。

5. DTO、领域对象和数据库行不是一回事

DTO 全称是 Data Transfer Object，中文常译为“数据传输对象”。它只负责在模块或系统边界传递一组明确字段，不应顺便执行数据库查询或业务流程。

  • API Schema 决定外部 JSON 长什么样；
  • Domain Model 表达业务状态及约束；
  • 数据库 Row 表达怎样落到表和字段。

三者看起来可能相似，但变化原因不同。API 为兼容客户端而变化，领域模型随业务变化，表结构随存储策略变化。显式转换会多一点代码，却避免框架类型渗透整个系统。

6. 为什么工作流不直接写数据库

LangGraph 节点产出 ResearchWorkflowUpdate；Application 再统一保存状态、材料和事件。这样工作流专注研究逻辑，数据库事务、取消保护和产品生命周期集中在应用层。未来换编排器时，HTTP API 与存储模型不用跟着重写。

7. 从装配入口读懂全局

app_factory.py 是组合根：它读取配置，创建数据库、适配器、工作流和应用服务，再把它们交给 FastAPI。理解一个分层项目时，先看组合根，再沿接口向内追，比从任意工具函数开始更容易建立全局图。

8. Composition Root 为什么集中装配

Composition Root 中文常称“组合根”，是选择具体实现并组装对象的少数位置。simulation 与 research 模式、Gemini 与 OpenAI-compatible Embedding 都在这里根据配置选择。

如果业务代码到处自己创建 HTTP 客户端和 Repository，测试很难换成 Fake，资源生命周期也难统一关闭。集中装配让依赖关系可见。

9. 怎样判断是否值得抽象

  1. 这个细节是否来自外部系统或可能替换？
  2. 调用方真正需要的最小能力是什么？
  3. 抽象是否隐藏了复杂度，而不是只转发同名方法？
  4. 能否让测试使用更简单的替代实现？
  5. 新增接口后，理解一次业务流程是否反而更困难？

ResearchFlow 为外部 I/O 和工作流设 seam，但没有给每个纯函数都建立类层级。

10. 当前架构的主动限制

  • 单进程后台 Task，不支持多实例分布式调度；
  • SQLite 与本地文件，适合单实例持久化；
  • LangGraph 无 Checkpointer，不做节点级恢复；
  • Demo 访问码不是多用户权限系统；
  • 接口降低替换影响，但无法消除供应商能力差异。
面试表达：项目采用模块化单体而不是微服务；通过 Application、Domain、Workflow、Integration 和 Persistence 分离职责，并在 LLM、搜索、Embedding 与工作流边界使用接口和适配器，使真实实现与 Fake 可以替换。
