## 1. 文档目的

本文记录 ResearchFlow 已经走过的阶段和未来实施顺序。它回答“接下来做什么、为什么按这个顺序做、做到什么程度算完成”。

- README 只展示当前状态和里程碑摘要；
- 本文维护每个里程碑的详细任务与完成标准；
- Git Commit 记录实际发生的代码和文档变化；
- 当前是个人项目，暂不额外维护 GitHub Issues。

`[x]` 表示已完成，`[ ]` 表示尚未完成。只有功能、测试和对应文档都达到完成标准后，才将里程碑标记为完成。

## 3. M0：模拟全栈纵向闭环

状态：已完成。

### 目标

不依赖 LLM、搜索服务或额外基础设施，先验证浏览器、前端、后端、持久化和实时事件能组成一个可运行闭环。

### 任务

- [x] 初始化可直接上传 GitHub 的 monorepo；
- [x] 实现 Next.js Dashboard 和 Research Workspace；
- [x] 实现 FastAPI 研究任务 API；
- [x] 使用 SQLite 保存任务、事件和模拟报告；
- [x] 使用 SSE 推送模拟工作流进度；
- [x] 支持刷新后重新打开研究历史；
- [x] 添加后端基础测试、前后端检查和中文项目文档。

### 完成标准

- 用户可以完成“创建任务 → 查看实时进度 → 查看报告 → 刷新重开”；
- 重启后端后，SQLite 中的研究历史仍然存在；
- 后端测试、Ruff、前端 ESLint 和生产构建通过；
- README、架构、运维和入门学习文档与实现一致。

## 4. M1：真实 LLM 接入与工程加固

状态：已完成。

### 目标

在不破坏模拟模式和离线测试的前提下，引入第一个真实模型调用，让 ResearchFlow 能根据用户目标生成结构化研究计划；同时修复 M0/M1 审查发现的契约、竞态、测试隔离和架构职责问题，为 M2 建立稳定边界。

### 实施顺序

1. 先定义框架无关的工作流和模型接口；
2. 使用 Fake 实现写测试，固定输入输出契约；
3. 再实现 OpenAI-compatible 远程模型适配器；
4. 将真实规划结果接入现有任务、事件和前端展示；
5. 最后补充错误、耗时和 Token 用量记录。

### 任务

- [x] 定义 ResearchFlow 自有的 `ResearchWorkflow` 和 `LLMClient` 接口；
- [x] 实现 OpenAI-compatible 远程 LLM 适配器；
- [x] 正式读取并校验模型、Base URL 和 API Key 配置；
- [x] 让 LLM 根据研究目标生成结构化研究计划；
- [x] 保留模拟实现和 Fake LLM，使本地测试不依赖真实 API；
- [x] 记录模型调用错误、耗时和基础 Token 用量；
- [x] 使用 OpenCode Zen `mimo-v2.5-free` 完成一次真实 API 冒烟测试；
- [x] 修复 SQLite 时间丢失 UTC 标记的问题；
- [x] 支持重新进入任务时恢复持久化研究事件；
- [x] 使用人类可读格式显示模型耗时和研究记录时间；
- [x] 拒绝纯空白研究目标，并统一 API 错误外壳；
- [x] 拆分无副作用应用工厂，使测试不在导入阶段读取 `.env`；
- [x] 修复 SSE 终态查询顺序和前端历史恢复竞态；
- [x] 使用统一 `research.event` 传输类型，移除前端领域事件白名单；
- [x] 让工作流产生 `ResearchWorkflowUpdate`，由 Application 统一持久化；
- [x] 添加前端 Vitest 基础测试；
- [x] 添加 GitHub Actions、MIT License 和公开演示输入；
- [x] 修正文案、领域术语、架构和运维文档。

### 完成标准

- 用户可以在配置有效时运行真实规划，在未配置密钥时继续运行模拟模式；
- 应用层不直接依赖某一家模型 SDK；
- 自动化测试不会访问外部模型，也不会消耗 API 额度；
- 配置错误和模型调用失败会产生明确、安全的错误信息；
- 工作流和 FastAPI 路由都不直接访问 Repository；
- 常规测试导入应用工厂时不读取 `.env`；
- 已终结运行的终结事件不会因查询竞态丢失；
- 新增领域事件不要求修改 EventSource 监听白名单；
- 后端测试、Ruff、前端 Vitest、ESLint 和生产构建通过；
- README、`.env.example`、运维手册和相关学习课程同步更新。

实现说明：自动化验证使用 Fake LLM 和 HTTP Mock，不访问真实供应商；用户配置支持严格 JSON Schema 的兼容服务后即可运行真实规划。M1 后续阶段仍保留模拟实现，这一边界会在界面和文档中明确展示。工程加固的详细记录见 [M1 工程加固复盘](retrospectives/pre-m2-hardening.md)。

M2 的实现与验证记录见 [M2 阶段复盘](retrospectives/m2.md)。

## 5. M2：LangGraph 与真实网页研究闭环

状态：已完成。

### 目标

用可控的 LangGraph 工作流完成规划、网页检索、正文读取、证据提取和写作的第一条真实研究链路。

### 任务

- [x] 在 `ResearchWorkflow` 接口后实现 `LangGraphResearchWorkflow`；
- [x] 建立规划、搜索、阅读、证据提取、写作和检查节点；
- [x] 接入一个网页搜索 Provider；
- [x] 读取、清洗和去重网页正文；
- [x] 在数据库中保存 Source、Evidence 和研究子任务；
- [x] 在 Research Workspace 展示真实来源和阶段性证据；
- [x] 将 Markdown 报告渲染为标题、表格、列表、代码和安全的可点击链接。

### 完成标准

- LangGraph 类型不会泄漏到 FastAPI、领域模型或前端契约；
- 至少可以对一个普通技术问题检索并读取多个真实网页来源；
- 关键中间产物可以持久化和重新打开；
- 搜索与网页读取失败具有有限重试和明确事件；
- 测试使用 Fake Provider，不依赖公开互联网稳定性。

## 6. M3：来源质量、可追溯引用和黄金演示场景

状态：已完成。

### 目标

在复用 Exa 通用 Web 检索的前提下，识别并归一化学术、官方、工业和社区来源，生成关键主张可追溯到证据的“AI 代码生成工具评测方案”。只有固定场景的检索质量证明现有能力不足时，才额外引入学术检索或元数据服务。

### 任务

- [x] 使用固定查询验证 Exa 对论文、官方文档、公开基准和企业资料的检索覆盖度，并据此决定是否需要额外学术能力；
- [x] 保存作者、发布时间和发布机构等可用元数据，将来源归一化为学术、官方、工业和社区等类型；
- [x] 建立主张与证据之间的引用关系；
- [x] 生成 Claim—Evidence 关系明确、引用覆盖可检查的 Markdown 报告；
- [x] 检查引用链接、来源覆盖度和无证据主张；
- [x] 在界面中区分来源类型，并展示关键主张对应的证据与来源；
- [x] 跑通“AI 代码生成工具评测方案”完整演示，保存固定输入和可公开展示的结果样例。

### 完成标准

- 报告中的关键主张能追溯到 Source 和 Evidence；
- 引用链接可点击，自动检查确认结构化主张旁存在完整引用链路，黄金样例再由人工抽查证据是否支持相邻主张；
- 黄金场景能够检索到学术、官方和工业界资料，来源类型在界面中可以区分；
- 是否引入额外学术检索或元数据服务由固定查询的覆盖度结果决定，而不是预先设为必选实现；
- 黄金场景报告包含评测目标、指标、数据集、流程、评分和风险；
- 保存一份可公开展示的固定演示输入和结果样例。

M3 的实现、真实服务验证和技术取舍见 [M3 阶段复盘](retrospectives/m3.md)。

## 7. M4：本地知识库与 RAG

状态：下一步。

进入本阶段前的基线问题、修复和设计约束见 [进入 M4 前审查](retrospectives/pre-m4-review.md)。

### 目标

允许用户选择自己的本地资料加入研究过程，并与 Exa 检索到的外部公开资料共同形成证据。

### 任务

- [ ] 支持上传首批文档格式，例如 PDF、Markdown 和纯文本，并限制文件类型、体积和数量，使用系统生成的安全存储名；
- [ ] 实现文档解析、分块和处理状态，保留原始文件名、页码或片段位置等来源信息；
- [ ] 用固定样例比较全文、向量或混合检索，选择低资源占用且效果足够的方案；
- [ ] 允许用户为一次研究选择要使用的文档或知识库范围；
- [ ] 在研究任务中联合检索所选本地资料与 Exa 外部资料，把两类命中统一转换为运行内 Source，再复用现有 Evidence 与 Claim 链路；
- [ ] 展示本地资料引用，并能定位回文件、页码或片段；
- [ ] 支持删除或重新处理文档，并清理对应分块、索引和关联数据。

### 完成标准

- 用户可以上传、查看处理状态和删除文档；
- 用户可以控制一次研究使用哪些本地资料；
- 检索结果保留文档、页码或片段位置等来源信息；
- 外部资料与知识库资料使用统一 Evidence 模型；
- Windows 本地运行不强制要求独立向量数据库或 GPU；
- 删除文档后，其分块、索引和关联数据能够一并清理。

### 实施顺序

M4 是当前最大的单个功能阶段，但不拆成新的里程碑。阶段内部依次完成：领域与存储边界、上传与解析生命周期、检索方案小样评测、工作流联合检索与引用、删除清理和完整验收。每一步都使用小规模固定文档集验证，向量检索只有在评测优于更轻方案时才进入主路径。

## 9. 当前不优先处理

以下内容并非永远不做，但在核心研究闭环稳定前不进入优先路径：

- 登录鉴权与多租户；
- PostgreSQL、Redis 和分布式任务队列；
- 多 Agent 自由对话；
- 本地模型训练或微调；
- Kubernetes 和复杂云基础设施；
- 大规模爬虫与高并发生产能力；
- 同时支持大量模型、搜索和文档 Provider。

## 10. 已确认与尚待确认的选择

已确认：

- M1 首个 OpenAI-compatible 模型服务使用 OpenCode Zen，并已用 `mimo-v2.5-free` 完成真实 API 冒烟测试。
- 通用网页搜索使用 Exa Search API，并通过 `SearchProvider` 保留未来更换付费服务的边界。
- 2026-08-26 的固定覆盖度评测中，Exa 对学术、官方和工业查询均达到当前门槛，因此 M3 不额外接入学术 Provider；专业元数据增强保持按需选项。

尚待确认：

- 首批文档格式和解析库；
- Embedding Provider 与轻量向量检索方案；
- 在线 Demo 的部署平台与预算。

这些选择应在对应里程碑开始前确认，不提前为了“可能需要”安装重型基础设施。

## 11. 更新与阶段复盘规则

- 开始里程碑前，确认目标、任务、完成标准和技术选择；
- 开发过程中只勾选已经实现并验证的任务；
- 新认识导致范围变化时直接修订本文，不保留失真的旧计划；
- 每完成一个里程碑，必须执行以下三轴阶段门禁审查：
  1. 实现质量：检查正确性、边界条件、测试缺口、错误处理、安全、资源占用、冗余代码和模块职责；
  2. 实现—文档一致性：逐项核对路线图完成标准、接口契约、架构文档、运行指南和实际行为，并清理过时内容；
  3. 设计演进：根据已经获得的实现认知，判断后续模型、接口、阶段范围和技术选择是否仍然合理，直接修订失真的设计；
- 将复盘结论写入 `docs/product/retrospectives/`，不依赖对话记忆；高风险问题在进入下一阶段前修复，合理延期项记录原因与处理里程碑；
- 完成里程碑后，同步更新 README 的“当前进度”和路线摘要；
- 实现、测试、文档、复盘和路线状态尽量放在同一个完整改动中提交；
- 项目进入多人协作前，不额外维护 GitHub Issues。
