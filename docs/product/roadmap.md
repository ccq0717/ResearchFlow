## 1. 文档目的

本文记录 ResearchFlow 已经走过的阶段和未来实施顺序。它回答“接下来做什么、为什么按这个顺序做、做到什么程度算完成”。

- README 只展示当前状态和里程碑摘要；
- 本文维护每个里程碑的详细任务与完成标准；
- Git Commit 记录实际发生的代码和文档变化；
- 当前是个人项目，暂不额外维护 GitHub Issues。

`[x]` 表示已完成，`[ ]` 表示尚未完成。只有功能、测试和对应文档都达到完成标准后，才将里程碑标记为完成。

## 3. M0：模拟全栈纵向闭环

状态：已完成。

### 目标

不依赖 LLM、搜索服务或额外基础设施，先验证浏览器、前端、后端、持久化和实时事件能组成一个可运行闭环。

### 任务

- [x] 初始化可直接上传 GitHub 的 monorepo；
- [x] 实现 Next.js Dashboard 和 Research Workspace；
- [x] 实现 FastAPI 研究任务 API；
- [x] 使用 SQLite 保存任务、事件和模拟报告；
- [x] 使用 SSE 推送模拟工作流进度；
- [x] 支持刷新后重新打开研究历史；
- [x] 添加后端基础测试、前后端检查和中文项目文档。

### 完成标准

- 用户可以完成“创建任务 → 查看实时进度 → 查看报告 → 刷新重开”；
- 重启后端后，SQLite 中的研究历史仍然存在；
- 后端测试、Ruff、前端 ESLint 和生产构建通过；
- README、架构、运维和入门学习文档与实现一致。

## 4. M1：真实 LLM 最小接入

状态：已完成。

### 目标

在不破坏模拟模式和离线测试的前提下，引入第一个真实模型调用，让 ResearchFlow 能根据用户目标生成结构化研究计划。

### 实施顺序

1. 先定义框架无关的工作流和模型接口；
2. 使用 Fake 实现写测试，固定输入输出契约；
3. 再实现 OpenAI-compatible 远程模型适配器；
4. 将真实规划结果接入现有任务、事件和前端展示；
5. 最后补充错误、耗时和 Token 用量记录。

### 任务

- [x] 定义 ResearchFlow 自有的 `ResearchWorkflow` 和 `LLMClient` 接口；
- [x] 实现 OpenAI-compatible 远程 LLM 适配器；
- [x] 正式读取并校验模型、Base URL 和 API Key 配置；
- [x] 让 LLM 根据研究目标生成结构化研究计划；
- [x] 保留模拟实现和 Fake LLM，使本地测试不依赖真实 API；
- [x] 记录模型调用错误、耗时和基础 Token 用量；
- [x] 使用 OpenCode Zen `mimo-v2.5-free` 完成一次真实 API 冒烟测试；
- [x] 修复 SQLite 时间丢失 UTC 标记的问题；
- [x] 支持重新进入任务时恢复持久化研究事件；
- [x] 使用人类可读格式显示模型耗时和研究记录时间。

### 完成标准

- 用户可以在配置有效时运行真实规划，在未配置密钥时继续运行模拟模式；
- 应用层不直接依赖某一家模型 SDK；
- 自动化测试不会访问外部模型，也不会消耗 API 额度；
- 配置错误和模型调用失败会产生明确、安全的错误信息；
- README、`.env.example`、运维手册和相关学习课程同步更新。

实现说明：自动化验证使用 Fake LLM 和 HTTP Mock，不访问真实供应商；用户配置支持严格 JSON Schema 的兼容服务后即可运行真实规划。M1 后续阶段仍保留模拟实现，这一边界会在界面和文档中明确展示。

## 5. M1.5：进入 M2 前工程加固

状态：已完成。

### 目标

修复 M0/M1 审查发现的契约、竞态、测试隔离和架构 seam 问题，让 M2 可以在稳定接口上增加 LangGraph 与真实研究事件。

### 任务

- [x] 拒绝纯空白研究目标，并统一 API 错误外壳；
- [x] 拆分无副作用应用工厂，使测试不在导入阶段读取 `.env`；
- [x] 修复 SSE 终态查询顺序和前端历史恢复竞态；
- [x] 使用统一 `research.event` 传输类型，移除前端领域事件白名单；
- [x] 让工作流产生 `ResearchWorkflowUpdate`，由 Application 统一持久化；
- [x] 添加前端 Vitest 基础测试；
- [x] 添加 GitHub Actions、MIT License 和公开演示输入；
- [x] 修正文案、领域术语、架构和运维文档。

### 完成标准

- 后端测试、Ruff、前端 Vitest、ESLint 和生产构建通过；
- 工作流和 FastAPI 路由都不直接访问 Repository；
- 常规测试导入应用工厂时不读取 `.env`；
- 已终结运行的终结事件不会因查询竞态丢失；
- 新增领域事件不要求修改 EventSource 监听白名单。

详细记录见 [进入 M2 前工程加固复盘](retrospectives/pre-m2-hardening.md)。

## 6. M2：LangGraph 与真实网页研究闭环

状态：下一步。

### 目标

用可控的 LangGraph 工作流完成规划、网页检索、正文读取、证据提取和写作的第一条真实研究链路。

### 任务

- [ ] 在 `ResearchWorkflow` 接口后实现 `LangGraphResearchWorkflow`；
- [ ] 建立规划、搜索、阅读、证据提取、写作和检查节点；
- [ ] 接入一个网页搜索 Provider；
- [ ] 读取、清洗和去重网页正文；
- [ ] 在数据库中保存 Source、Evidence 和研究子任务；
- [ ] 在 Research Workspace 展示真实来源和阶段性证据。

### 完成标准

- LangGraph 类型不会泄漏到 FastAPI、领域模型或前端契约；
- 至少可以对一个普通技术问题检索并读取多个真实网页来源；
- 关键中间产物可以持久化和重新打开；
- 搜索与网页读取失败具有有限重试和明确事件；
- 测试使用 Fake Provider，不依赖公开互联网稳定性。

## 7. M3：学术检索、引用和黄金演示场景

状态：计划中。

### 目标

让产品能够综合学术界和工业界来源，生成带可追溯引用的“AI 代码生成工具评测方案”。

### 任务

- [ ] 接入至少一个学术论文来源；
- [ ] 合并网页、论文和公开基准的检索结果；
- [ ] 建立主张与证据之间的引用关系；
- [ ] 生成带可点击引用的 Markdown 报告；
- [ ] 检查引用链接、来源覆盖度和无证据主张；
- [ ] 跑通“AI 代码生成工具评测方案”完整演示。

### 完成标准

- 报告中的关键主张能追溯到 Source 和 Evidence；
- 引用链接可点击，且引用内容能够支持相邻主张；
- 学术来源和工业界来源在界面中可以区分；
- 黄金场景报告包含评测目标、指标、数据集、流程、评分和风险；
- 保存一份可公开展示的固定演示输入和结果样例。

## 8. M4：本地知识库与 RAG

状态：计划中。

### 目标

允许用户把自己的资料加入研究过程，并与网页、论文来源共同形成证据。

### 任务

- [ ] 支持上传首批文档格式，例如 PDF、Markdown 和纯文本；
- [ ] 实现文档解析、分块和处理状态；
- [ ] 选择低资源占用的 Embedding 与向量检索方案；
- [ ] 在研究任务中联合检索个人知识库与外部资料；
- [ ] 展示知识库来源，并支持删除或重新处理文档。

### 完成标准

- 用户可以上传、查看处理状态和删除文档；
- 检索结果保留文档、页码或片段位置等来源信息；
- 外部资料与知识库资料使用统一 Evidence 模型；
- Windows 本地运行不强制要求独立向量数据库或 GPU；
- 删除文档后，其向量和关联数据能够一并清理。

- [ ] 提供可复现的前后端容器构建和本地部署拓扑；
- [ ] 确认在线 Demo 的部署平台、区域、持久磁盘和月度预算；

## 10. 当前不优先处理

以下内容并非永远不做，但在核心研究闭环稳定前不进入优先路径：

- 登录鉴权与多租户；
- PostgreSQL、Redis 和分布式任务队列；
- 多 Agent 自由对话；
- 本地模型训练或微调；
- Kubernetes 和复杂云基础设施；
- 大规模爬虫与高并发生产能力；
- 同时支持大量模型、搜索和文档 Provider。

## 11. 已确认与尚待确认的选择

已确认：

- M1 首个 OpenAI-compatible 模型服务使用 OpenCode Zen，并已用 `mimo-v2.5-free` 完成真实 API 冒烟测试。

尚待确认：

- 首个网页搜索 Provider；
- 首个学术论文数据来源；
- 首批文档格式和解析库；
- Embedding Provider 与轻量向量检索方案；
- 在线 Demo 的部署平台与预算。

这些选择应在对应里程碑开始前确认，不提前为了“可能需要”安装重型基础设施。

## 12. 更新与阶段复盘规则

- 开始里程碑前，确认目标、任务、完成标准和技术选择；
- 开发过程中只勾选已经实现并验证的任务；
- 新认识导致范围变化时直接修订本文，不保留失真的旧计划；
- 每完成一个里程碑，必须暂停并检查实现、测试、接口、安全、资源占用和文档是否存在问题；
- 将复盘结论写入 `docs/product/retrospectives/`，高风险问题在进入下一阶段前修复，合理延期项记录原因与处理里程碑；
- 完成里程碑后，同步更新 README 的“当前进度”和路线摘要；
- 实现、测试、文档、复盘和路线状态尽量放在同一个完整改动中提交；
- 项目进入多人协作前，不额外维护 GitHub Issues。
