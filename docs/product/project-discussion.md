# ResearchFlow 项目讨论文档

> 状态：讨论中
> 更新日期：2026-08-23

## 1. 项目背景

ResearchFlow 是一个面向科研与技术预研场景的 AI 深度研究工作台。用户输入一个相对开放的研究目标，系统自动拆解研究问题，检索互联网、学术论文和用户知识库中的资料，提取证据并总结，最终生成带有可追溯引用的结构化研究报告或方案文档。

本项目的主要目标是：

1. 作为 AI 全栈工程师求职作品，能够完整运行、演示和讲解；
2. 在开发过程中系统学习前端、后端、数据库和 AI 应用工程；
3. 展示从产品需求、系统设计到开发、测试和部署的完整工程能力；
4. 在 Windows 电脑上以较低资源占用运行。

## 2. 产品定位与使用范围

ResearchFlow 不追求成为覆盖所有行业的通用 Agent 平台，而是聚焦“需要搜集资料、分析证据并形成结构化成果”的研究任务。

典型用途包括：

- 构思和完善科研 Idea；
- 跟踪前沿技术与产业动态；
- 调研某个技术方向的学术界和工业界进展；
- 对论文、网页和个人资料进行联合研究；
- 形成技术选型、竞品分析、文献综述或评测方案。

目标用户包括研究生、高校教师、科研人员、企业预研团队和技术决策人员。

## 3. 黄金演示场景

首个完整演示场景为：**设计“AI 代码生成工具的评测方案”**。

用户输入类似目标：

> 调研学术界和工业界对 AI 代码生成工具的评测方法，分析已有论文、基准和产品实践，并为企业设计一份覆盖代码质量、任务完成能力、安全性和开发效率的评测方案。

系统执行过程：

1. 理解研究目标和输出要求；
2. 拆解研究子问题，例如评测对象、指标、数据集、实验设计和风险；
3. 搜索学术论文、公开基准、技术报告和工业界资料；
4. 查询用户上传的论文或内部知识库；
5. 读取资料并提取与子问题相关的证据；
6. 总结已有评测方法、共识、差异和不足；
7. 检查是否存在证据不足的研究问题，并在预算范围内补充检索；
8. 生成带引用的调研总结；
9. 进一步输出一份可执行的 AI 代码生成工具评测方案。

最终成果至少包含：

- 背景与评测目标；
- 学术界和工业界现状综述；
- 评测对象与使用场景；
- 指标体系及指标定义；
- 数据集与任务设计；
- 实验流程与对照设计；
- 结果统计和评分方法；
- 安全、隐私与代码许可证风险；
- 实施计划与资源需求；
- 可点击、可追溯的参考来源。

## 4. 核心工作流

```text
研究目标输入
    ↓
目标澄清与约束提取
    ↓
研究计划与子任务生成
    ↓
网页 / 学术论文 / RAG 知识库检索
    ↓
正文读取、清洗与去重
    ↓
证据和主张提取
    ↓
覆盖度检查与有限补充检索
    ↓
调研总结与方案写作
    ↓
引用验证
    ↓
保存并展示最终文档
```

系统应采用可控的阶段式工作流，而不是让多个 Agent 无限制自由对话。每一步应有明确的输入、输出、状态和失败处理方式。

## 5. MVP 的含义

MVP 是 Minimum Viable Product，即“最小可行产品”。它不是粗糙或不可用的半成品，而是用最少功能完成一个可真实演示的端到端闭环。

“MVP 页面”指第一版为了完成这个闭环必须具备的最少页面和界面，不代表最终产品只能有这些页面。

### 5.1 建议的 MVP 页面

#### 页面一：研究首页 / Dashboard

- 输入新的研究目标；
- 展示历史研究任务；
- 查看任务状态和最近更新时间；
- 打开已有研究。

#### 页面二：研究工作台 / Research Workspace

- 展示研究目标和研究计划；
- 实时展示当前执行阶段与进度；
- 展示各个研究子任务的状态；
- 展示研究事件、失败信息和重试操作；
- 允许取消正在进行的任务；
- 展示来源、证据和阶段性结论；
- 展示最终调研报告或评测方案。

这是整个产品最重要的页面，可以通过标签页或分栏组织计划、过程、来源和报告，不需要拆成多个独立页面。

#### 页面三：知识库 / Knowledge Base

- 上传 PDF、Markdown 或文本资料；
- 查看文件处理状态；
- 查看、删除或重新处理资料；
- 在研究任务中选择要使用的知识库。

#### 页面四：设置 / Settings

- 配置模型和搜索服务；
- 设置研究深度、并发数和预算上限；
- 展示配置是否可用。

第一版也可以将设置放在 `.env` 文件中，把独立设置页面推迟到第二阶段。这样 MVP 实际只需要三个主要页面。

## 6. MVP 功能边界

第一版必须完成：

1. 创建研究任务；
2. 生成 3～5 个结构化研究子任务；
3. 检索网页和学术资料；
4. 检索一个小型本地知识库；
5. 保存来源、证据片段和子任务总结；
6. 通过 SSE 实时推送研究进度；
7. 生成带可点击引用的 Markdown 报告；
8. 保存并重新打开研究历史；
9. 支持取消、有限重试和明确错误状态；
10. 提供 Windows 启动说明、基础测试和项目 README。

第一版暂缓：

- 多租户计费与复杂权限系统；
- 多个 Agent 的自由协作或群聊；
- 大规模分布式爬虫；
- 本地大模型训练或微调；
- Redis、Kubernetes 等非必要基础设施；
- 同时支持大量文档格式和搜索供应商；
- 面向生产环境的高并发能力。

## 7. 初步技术路线

```text
Frontend
Next.js + React + TypeScript
Tailwind CSS + shadcn/ui

Backend
Python + FastAPI
Pydantic + SQLAlchemy

AI Workflow
LangGraph 或显式状态机
OpenAI-compatible LLM abstraction

Storage (MVP)
SQLite + 本地文件存储
轻量词法检索，可替换的检索接口

Communication
REST API + SSE

Development
Windows 原生运行
Docker 作为可选部署方式
```

低资源原则：默认调用云端 LLM，不要求本地 GPU，不把 Embedding API、Redis、独立向量数据库或 Docker Desktop 作为本地开发前提。只有固定评测证明语义检索有收益时才增加 Embedding 服务。

## 8. 简历价值要求

ResearchFlow 只有在体现独立设计与工程能力时，才比复刻教程更有价值。最终项目应具备：

- 可运行的完整前后端闭环；
- 清晰的项目定位、README 和架构图；
- 可追溯到原始资料的证据与引用；
- 研究历史、任务状态恢复、取消与重试；
- Web 与知识库的混合检索；
- 核心工作流测试与前端关键交互测试；
- 延迟、Token、费用和检索质量的基础度量；
- Windows 一键或少步骤启动方式；
- 演示视频或可访问的在线 Demo。

## 9. 后续需要讨论和确认的问题

1. 第一版是否实现简化登录，还是先做单用户模式；
2. 报告是否只支持 Markdown，还是同时导出 PDF / DOCX；
3. 研究任务的最大轮数、来源数和成本预算；
4. 如何进一步验证引用的语义正确性和报告质量；
5. 在线 Demo 的平台、访问保护和月度预算。

## 10. 当前决定

- 项目名称：ResearchFlow；
- 核心场景：科研和技术预研；
- 黄金演示任务：AI 代码生成工具评测方案；
- 主要目标：AI 全栈求职作品，同时学习前后端开发；
- 本地环境：Windows；
- 资源策略：云端模型、本地轻量服务、可选生产化组件；
- 产品策略：先完成可演示的单机 MVP，再逐步加入工程化能力；
- 资料来源：Exa 通用 Web 搜索与 PDF、Markdown、UTF-8 文本本地知识库；
- 本地检索：默认词法检索，不预先引入 Embedding 或独立向量数据库；
- 工作流编排：使用 LangGraph，但通过 ResearchFlow 自己的工作流接口隔离框架；
- 仓库形式：以前后端分离的 monorepo 组织，工作空间根目录即 GitHub 仓库根目录；
- 目录原则：应用放在 `apps/`，各应用源码放在自己的 `src/`，项目资料统一放在 `docs/`。
